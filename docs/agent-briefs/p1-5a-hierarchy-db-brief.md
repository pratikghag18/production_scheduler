## 5. Structural invariants (D67–D69)

### 5.1 `(org_id, path)` unique index — D67

```sql
CREATE UNIQUE INDEX nodes_org_path_unique ON nodes (org_id, path);
```

Closes F3, F4 and therefore F4a as a database invariant. **Verified: the existing seed satisfies
it**, so this index creates cleanly on a seeded database.

### 5.2 Cycle rejection — D68

A `BEFORE INSERT OR UPDATE OF parent_id` row trigger on `nodes` that raises
`api_raise('node_cycle', …)` when:

- `NEW.parent_id = NEW.id` (covers INSERT as well as UPDATE), or
- on UPDATE, the new parent's `path` is contained by `OLD.path` (`v_parent_path <@ OLD.path`)

**Name it `nodes_before_cycle`.** Postgres fires same-timing triggers in **trigger-name order**,
and this must run before the existing `nodes_before_path` so it sees a coherent `OLD.path`.
`nodes_before_cycle` < `nodes_before_path` alphabetically. The name is load-bearing; do not
rename it to something that sorts later.

### 5.3 Level adjacency — D69

A `BEFORE INSERT OR UPDATE OF parent_id, level_id` row trigger, named `nodes_before_level`,
raising `api_raise('level_mismatch', …)` unless:

- `parent_id IS NULL` **and** the node's level position is 0, or
- the node's level position is exactly the parent's level position + 1

**With one documented escape hatch:** return early when
`coalesce(current_setting('app.hierarchy_migration', true), '') = 'on'`. §2 deliberately kept this
rule out of the schema and migration 0001 carries a *do not add it here later* note — that note
was protecting the **Phase-3 mid-level-insertion tool**, not the invariant itself. The escape
hatch is what lets that tool run later; D69 amends the note rather than ignoring it. Say so in a
comment next to the trigger, referencing design plan §19 D69.

The `DETAIL` payload for this trigger **must include `node_id`.** That key is what distinguishes a
trigger rejection from an RPC pre-check rejection, and case N17 asserts on it.

## 6. The five RPCs

All five: `LANGUAGE plpgsql`, **`SECURITY INVOKER`**, `SET search_path = public, pg_temp`, every
error through `api_raise`. Argument names exactly as written — PostgREST binds by name.

### 6.1 `save_hierarchy_levels(p_levels jsonb) RETURNS jsonb` — D70

`p_levels` is an **ordered array**; the array index *is* the position:

```json
[{"id": "uuid or null", "name": "Site", "is_schedulable": false}, …]
```

`id: null` means a new level. A level present in the database but absent from `p_levels` is being
removed. Because position comes from array order, a payload cannot express a gap — there is no
"positions must be contiguous" check to write.

Validate, in this order, each raising the code named:

1. caller is not an admin (`app_is_admin()`) → `not_permitted`
2. `p_levels` is not a JSON array → `invalid_argument`
3. empty array → `invalid_argument`
4. more than **64** entries → `invalid_argument`
5. the number of entries with `is_schedulable = true` is not exactly 1 → `invalid_argument`
6. any entry whose trimmed name is empty → `invalid_argument`
7. a level being removed still has nodes → `level_in_use`
8. the schedulable level is changing **and** scheduled work exists on the old schedulable level →
   `schedulable_level_locked` (see D72 below)

Then write, **in three passes** — this is F1/F2 and there is no way around it:

1. `UPDATE hierarchy_levels SET is_schedulable = false WHERE org_id = …`
2. `UPDATE hierarchy_levels SET position = position + 1000 WHERE org_id = …`
3. loop the array in order: `UPDATE` existing rows to their final `position`/`name`, `INSERT` rows
   whose `id` is null; then `DELETE` the removed ids; then set `is_schedulable = true` on the one
   level at the new schedulable position

The 64-entry cap exists so the +1000 offset can never collide with a final position.

**D72, the schedulable lock:** count runs on nodes at the old schedulable level; **if that is
zero, also count assignments.** Both halves are required — after P1-4e a direct assignment can
exist with no run at all, and a mutation that drops the assignments half was measured to be caught
by nothing until case L12 was added. Raise with `blocking_rows` in the detail.

Returns the full level list as a jsonb array of
`{id, position, name, is_schedulable}`, ordered by position.

### 6.2 `create_node(p_parent_id uuid, p_name text, p_sort_order int DEFAULT 0) RETURNS jsonb`

- blank/whitespace name → `invalid_argument`
- `p_parent_id IS NULL` → the node takes the org's position-0 level; its prospective path is
  `slugify(name)`
- otherwise: the parent must exist in the caller's org (`invalid_argument` if not); the node's
  level is the level at *parent position + 1*; if no such level exists → `level_mismatch`; the
  prospective path is `parent.path || slugify(name)`
- if any node in the org already has that path → `path_collision`, with `path` and
  `existing_node_id` in the detail
- insert with the trimmed name; **do not set `path`** — the existing `nodes_before_path` trigger
  derives it (D6)

Returns `{id, name, path, parent_id, level_id, sort_order, active}`.

### 6.3 `rename_node(p_node_id uuid, p_name text) RETURNS jsonb`

- blank name → `invalid_argument`; unknown node → `invalid_argument`
- compute the prospective path (same parent prefix, new slug); if another node in the org already
  holds it → `path_collision`. **Exclude the node itself** from that check, or renaming a node to
  its own current name fails
- `UPDATE nodes SET name = …`; descendant paths cascade via the existing `nodes_after_path`
  trigger — verified, do not reimplement the cascade

Returns `{id, name, path}`.

### 6.4 `move_node(p_node_id uuid, p_new_parent_id uuid, p_sort_order int DEFAULT NULL) RETURNS jsonb` — D71

**Never changes `level_id`.** The new parent must be exactly one level above the node's *existing*
level. Checks, in this order:

1. unknown node → `invalid_argument`
2. `p_new_parent_id IS NULL`: allowed only if the node is already at level position 0, else
   `level_mismatch`
3. `p_new_parent_id = p_node_id` → `node_cycle`
4. unknown parent → `invalid_argument`
5. the new parent's path is contained by the node's path → `node_cycle`
6. the node's level position is not the parent's + 1 → `level_mismatch`
7. the prospective path is taken by another node → `path_collision`

Then `UPDATE nodes SET parent_id = …, sort_order = coalesce(p_sort_order, sort_order)`.

**Order 5 before 6 and keep it that way.** Measured: *every* move beneath one's own descendant
also skips a level, so with the level test first a genuine cycle would be reported as
`level_mismatch`. The cycle pre-check is load-bearing for error quality; §5.2's trigger is what
makes it safe.

**The `DETAIL` for check 6 must NOT contain `node_id`** — that is what tells it apart from the
trigger's rejection, and case N17 asserts the key is absent.

Returns `{id, name, path, parent_id, sort_order}`.

### 6.5 `delete_node(p_node_id uuid, p_mode text DEFAULT 'deactivate') RETURNS jsonb` — D73

- `p_mode` not in (`'deactivate'`, `'delete'`) → `invalid_argument`; unknown node →
  `invalid_argument`
- **`'deactivate'`**: `UPDATE nodes SET active = false WHERE org_id = … AND path <@ <node path>` —
  the **whole subtree**, not just the node. Returns `{mode: 'deactivate', deactivated: <count>}`
- **`'delete'`**: refuse with `node_in_use` if the node has descendants, runs, or assignments,
  putting `children`, `runs` and `assignments` counts in the detail. Otherwise delete the node's
  `profile_grants`, `node_shift_templates` and `node_skill_requirements` rows, then the node.
  Returns `{mode: 'delete', deleted: 1}`

## 7. Error contract (D74)

Six codes join the closed set. All route through `api_raise`, so all map to `PT409`:

`path_collision` · `node_cycle` · `level_mismatch` · `level_in_use` · `node_in_use` ·
`schedulable_level_locked`

surface.** Clients switch on the JSON `error` field (§17.2 item 3, `docs/api.md` §1), and `23505`
is not in that contract. The unique index and the triggers are the backstop for writes that do not
go through an RPC — they are not the primary error path.

Add all six to `docs/api.md`'s error table, with the RPCs that raise each.

## 14. Known traps, all hit for real while writing this brief

1. **A table alias that shadows a declared PL/pgSQL variable.** `SELECT count(*) … FROM runs r
   JOIN nodes n` inside a function that also declares `r record` fails with `record "r" is not
   assigned yet` (SQLSTATE 55000) — PL/pgSQL resolves the alias against the variable. It is
   invisible until that exact branch runs, and here it only runs when the schedulable level
   changes. Alias those tables something else.
2. **Trigger firing order is alphabetical by trigger name** — see §5.2.
3. **`UPDATE OF <cols>` matches the statement's own SET clause**, not what a BEFORE trigger
   computed. Migration 0001's `nodes_after_path` carries a long note about this; read it before
   assuming anything about when the cascade fires.
4. **`REVOKE … FROM anon` is not enough** — see §8.
5. **`SECURITY INVOKER` functions calling `auth.uid()` need `USAGE ON SCHEMA auth`.** Already
   granted in the harness; do not remove it.
6. **The seed is anchored to the week it was run.** Irrelevant to this brief's cases (none depend
   on the current date) but do not "fix" a board that looks empty — that is a seed anchor, not a bug.
