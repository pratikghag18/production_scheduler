## Expected

R-039 (`stated_by: maintainer`, §16.1, D12): *"A shift template is a named
daily pattern of shifts, each with breaks. It attaches to any node and
inherits downward; the nearest ancestor with a template wins."* R-D101 says
the same in the other direction: *"Which pattern a node runs is still resolved
by nearest ancestor up the tree; ownership decides who may edit a pattern, not
which one applies."*

Plant A's template is attached at `plant_a` (the only `node_shift_templates`
row under Plant A). Line 1, Cell 1 and Cell 2 sit under it, so every one of
them runs that pattern — for Dana and for Ana alike. The board of the person
who schedules Line 1 should draw the same breaks and boundaries, snap to the
same shift edges, and offer the same shift chips as the plant admin's.

## Lead

A suspicion, not a fact. `board_window` (0058, the last definition) builds
`node_template_map AS (SELECT sn.id, resolve_shift_template(sn.id) FROM
scoped_nodes sn)`, and `resolve_shift_template` (last definition 0023) is a
plain `LANGUAGE sql STABLE` function — **SECURITY INVOKER** — that joins
`nodes anc ON target.path <@ anc.path` and `node_shift_templates nst ON
nst.node_id = anc.id`. Under Ana's session both the ancestor node `plant_a`
(`nodes_select` is descendants-of-grant) and the attachment row on it
(`node_shift_templates_select` is `app_can_read_node(node_id)`) are filtered
away, so the walk finds nothing and the resolver answers NULL for a node that
does have a pattern. The same question for settings was answered in 0050 by
making `app_resolve_node_setting` SECURITY DEFINER — it returns `ymd_slash`
for Ana above — and for people in 0058 by `app_operator_homes`. The smallest
fix is the same one: re-emit `resolve_shift_template` as SECURITY DEFINER with
a pinned `search_path` (it takes a node id and returns a template id, so the
tenant boundary is the node's org, which the caller cannot choose), and let
`board_window` keep calling it. The template's own row is already readable by
her, so the `shift_templates` array follows once the map does.

The pin reads the migrations: the last definition of `resolve_shift_template`
must be SECURITY DEFINER, and it proves its reader by finding
`app_resolve_node_setting`'s. A fix that resolves through a different helper
would leave the pin red and should say so in the developer note.

## Developer note

Agreed, and the lead is the fix. 0061 re-emits `resolve_shift_template`
whole from its last definition (0005; 0023 only re-grants it) as SECURITY
DEFINER with a pinned search path and the org term first, so a node in another
company or a uuid that exists nowhere answers NULL; the signature is unchanged
and every caller passes a node id. Eight cases in
`84_shift_pattern_resolves_upward_test.sql`, red before and green after; the
pin green; the Reproduction replayed live (`resolve_shift_template(line_1)`
answers the plant's pattern as Ana; her board window carries three mapped
nodes and the template) and driven in the browser: break bands and boundaries
drawn, the three shift chips offered. The class of mistake is now written
into CLAUDE.md section 4, and `e2e/roleWalk.spec.ts` asserts Ana's create form
offers exactly Dana's shift chips, so the next one of these goes red before
a commit rather than in your round.
