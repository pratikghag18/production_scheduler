## Reproduction

On a fresh stack (`supabase db reset`), signed in as `ana@example.test` (`devpassword`), a Line 1
supervisor on Plant A:

1. Go to `/admin`, open the **Absences** tab.
2. In **Person**, pick the first operator (the create form's `selectOption({ index: 1 })`).
3. Fill **From**, **To**, a **Reason**, and click **Record absence**.

Automated form: `npx playwright test e2e/absenceOnBoard.spec.ts --project=chromium --workers=1`.

Confirmed on a pristine, isolated, serial run (not contention, not pollution — `weekTemplates` in
the same clean-room run passed).

## Expected

R-357's claim: *"An absence is recorded in the app ... and the board and Copy Week treat it as a
clash."* The spec's own words: Ana *"records an absence for someone she can place over the shown
week ... and reads that the person is marked on leave."* After **Record absence**, the new row must
appear in the Absences list, and the operator must show as on leave on the board.

## Actual

`e2e/absenceOnBoard.spec.ts` picks the Person at `selectOption({ index: 1 })` — the first offered
operator — records, and times out because the row never appears:

```
Error: expect(locator).toBeVisible() failed
Locator: getByRole('row').filter({ hasText: 'E2E on-board leave 1790003931703' })
Error: element(s) not found
```

**Correction to the first read of this defect:** the write is NOT a silent no-op. `set_absence` is a
SECURITY DEFINER RPC that raises loudly, and `AbsencesPanel` surfaces the error
(`addMutation.onError → setFormError`, rendered in a `role="alert"`). Driving `set_absence` directly
as Ana over the six operators she is offered (this week, 14 days) shows the server behaving correctly:

```
ana@example.test sees 6 operators (the whole plant, via the operators SELECT policy)
  set_absence(Operator A1) -> RAISED PT409 "this person already has an absence over some of those days"
  set_absence(Operator A2) -> OK wrote a row
  set_absence(Operator A3) -> RAISED PT403 "you cannot record an absence for someone at that place"
  set_absence(Operator A4) -> RAISED PT403 "..."   A5, A6 -> same PT403
viva@example.test (viewer) -> all six RAISED PT403   (viewer boundary holds)
```

So Ana can record for only some of the people the dropdown offers her (A2, on her line), and the
first offered person is one the server refuses (PT403) or that overlaps (PT409). The screen offers
what the server refuses. The spec's own comment — *"the first person Ana may place"* — shows it was
written expecting the dropdown to already be filtered to placeable people; it is not, so index 1 is
not recordable and R-357's e2e proof fails on the current seed. (The single row in `absences` after
a failed run is the seeded one; the earlier "0 E2E rows" reading was correct but was mis-explained as
a silent server no-op.)

## Lead

**A lead, not a fact — the developer decides, and there is a direction call here for the maintainer.**
The Person dropdown lists `visiblePeople = rowsInPlant(operators, ...)` — everyone in the plant Ana
can SEE (`AbsencesPanel.tsx:110`, `:284`) — but `set_absence` only lets her record for people she can
PLACE (it raises `not_permitted` / PT403 at the guard on line ~65 of the function). Per CLAUDE.md §4
("whatever a client offers must be decided by the same test the server runs"), the fix is probably to
filter the dropdown to the operators `set_absence` would accept — the same placeability predicate —
so a supervisor is never offered someone the server will refuse. The panel's header comment defends
the opposite (offer all, let the server refuse, show the error), so this is a genuine design call:
either filter the dropdown (align with §4, and `absenceOnBoard.spec.ts` index 1 then lands on a
placeable person) or change the spec to select a known-placeable operator by name rather than by
index. Note the server and the error-surfacing are already correct — this is not a data or security
problem, which is why it is filed minor.

## Developer note

21 Sept (session 182). The maintainer sided with the filter. The Person list is decided by
`canEditNode` (through `useEditRights`) on `homeNodeId ?? siteNodeId`, the same coalesce
`set_absence` runs; it fails open and a refusal is still worded. The pin is
`src/test/defects/DEF-0035.test.tsx` (the offered and the withheld person, the fail-open case, the
null-home case). Found on the way: `absence_overlap` was not in the client's closed set of codes,
so an overlap read "Something went wrong" (F-185, fixed in the same commit); and the absenceOnBoard
spec left its row behind whenever it died before its cleanup, so it now clears its own leftovers
first.

## Tester note — REOPENED 21 Sept (session 183t)

The fix does not hold against the real app. Re-ran the reproduction cold on a fresh `supabase db
reset`, signed in as Ana: `e2e/absenceOnBoard.spec.ts` still fails, and the failure page shows the
**Person dropdown offering all six operators** (John Kim, Lena Novak, Maria Lopez, Priya Shah, Sam
Patel, Tom Baker), unfiltered, with John Kim selected at index 1:

```
- combobox "Person":
  - option "Choose a person…"
  - option "John Kim" [selected]
  - option "Lena Novak"
  - option "Maria Lopez"
  - option "Priya Shah"
  - option "Sam Patel"
  - option "Tom Baker"
- alert: You do not have edit rights on this cell.
```

Driving `set_absence` directly as Ana on the same fresh seed shows the server accepts only two of
those six (Sam Patel and Maria Lopez, both on her line) and refuses the other four with PT403. So the
create form still offers four people the server refuses — the exact symptom this defect names — and
index 1 (John Kim) is one of them.

The `DEF-0035.test.tsx` pin passes because it **mocks `useEditRights`** with a known result, so the
filter narrows in the test. In the real app `canEdit` fails OPEN for Ana across all six
(`AbsencesPanel.tsx:149` `visiblePeople.filter((p) => canEdit(...))`), which the panel's own header
comment now admits ("IT STILL FAILS OPEN ... the fail-open case still offers a person the server may
go on [to refuse]"). The filter is therefore a no-op for a line supervisor, which is precisely the
role the defect was filed against. Lead: the reopen is about `useEditRights`/`canEditNode` returning
fail-open (or `true`) for Ana's own line's people while `set_absence` narrows to two — the client
preview and the server disagree; the pin must exercise the REAL hook against a signed-in supervisor,
not a mock, or it cannot catch this. R-357 stays contradicted.

A RED reproduction pin now exists: `src/test/defects/DEF-0035-reopen.test.ts`. It runs the create
form's own filter expression over the REAL `canEditNode` with the data measured live above — Ana's
grant (`writablePaths = ["plant_a.area_1.line_1"]`, `known: true`) and the six operators, four of
whom resolve to a null path because their owning node is not one a line supervisor may read. It
asserts the form offers only the two the server accepts; today it offers all six, so it fails. It
goes green when the client offers only the people `set_absence` accepts — by resolving the owning
path for these people or filtering by the server's own answer — WITHOUT breaking the deliberate
fail-open on a genuinely unresolved node.
