## Reproduction

On a fresh stack (`supabase db reset`), signed in as `ana@example.test` (`devpassword`), a Line 1
supervisor on Plant A:

1. Go to `/admin`, open the **Absences** tab.
2. In **Person**, pick the first operator (the create form's `selectOption({ index: 1 })`).
3. Fill **From**, **To**, a **Reason**, and click **Record absence**.

Automated form: `npx playwright test e2e/absenceOnBoard.spec.ts --project=chromium --workers=1`.

Confirmed on a pristine, isolated, serial run (not contention, not pollution — `weekTemplates` in
the same clean-room run passed).

## Expected

R-357's claim: *"An absence is recorded in the app ... and the board and Copy Week treat it as a
clash."* The spec's own words: Ana *"records an absence for someone she can place over the shown
week ... and reads that the person is marked on leave."* After **Record absence**, the new row must
appear in the Absences list, and the operator must show as on leave on the board.

## Actual

The new row never appears. `e2e/absenceOnBoard.spec.ts` fails at the first check after recording:

```
Error: expect(locator).toBeVisible() failed
Locator: getByRole('row').filter({ hasText: 'E2E on-board leave 1790003931703' })
Expected: visible
Error: element(s) not found
```

And nothing was written to the database — read back as the postgres superuser (so this is not an
RLS-hidden row, it genuinely does not exist):

```
select count(*) from absences where reason like 'E2E%';   -- 0
select count(*) from absences;                             -- 1  (the single seeded row only)
```

No error is surfaced in the UI. So the write reports nothing wrong and changes nothing — the person
is never marked on leave.

## Lead

**A lead, not a fact — the developer decides.** `absences` has RLS on with only a SELECT policy
(`absences_select`); every write goes through the `set_absence` SECURITY DEFINER RPC
(`src/lib/api/absences.ts` `setAbsence` → `supabase.rpc("set_absence")`, which does
`if (error) throw toSchedulerError(error)`). No error was thrown and zero rows landed, so
`set_absence` most likely **inserted zero rows for Ana's chosen operator without raising** — a
scope/eligibility guard inside the definer that no-ops instead of refusing loudly — and `setAbsence`
treats the empty result as success. This is the project's own "a write that reports success can have
changed nothing" trap (CLAUDE.md §4): read `ROW_COUNT` back inside `set_absence` and raise when it
is zero. The other candidate to rule out: the **Person** dropdown may be offering Ana an operator
she has no right to record for (it lists `rowsInPlant` — the whole plant — while a Line 1 supervisor
may only place her line), i.e. the screen offers what the server refuses; check whether the operator
at index 1 is one Ana may actually place, and whether `set_absence` guards on that.
