## Reproduction

At tip `03700f1`, with the tester's own stack freshly reset (`node scripts/tester-stack.mjs up`,
which runs `supabase db reset` and re-seeds `dev_demo.sql` against whatever `now()` is at that
moment) on any day of the week that is Thursday, Friday, Saturday or Sunday:

```
node scripts/tester-run.mjs --sql --e2e
```

or directly:

```
npx playwright test e2e/weekTemplates.spec.ts --project=chromium
```

## Expected

`dev_demo.sql`'s own section 6 header (`supabase/dev_demo.sql:407-411`): *"A WEEK OF SCHEDULE, so
no board opens empty ... Anchored on `date_trunc('week', now())`, so it is always the current week
rather than a fixed date that drifts into the past."* R-356's own `verified_by` lists
`e2e/weekTemplates.spec.ts` as browser proof that saving the current week as a template and
applying it through Copy Week works; that spec's flow depends on the board actually showing a
non-empty week when it opens on "today" (`signIn(page, ADMIN, "/")` with no date navigation), which
the file's own comment promises will always be true.

## Actual

```
  1) [chromium] › e2e\weekTemplates.spec.ts:78:1 › an admin saves this week as a template and applies it through Copy Week

    Error: expect(locator).toBeVisible() failed

    Locator: getByRole('dialog', { name: 'Copy week' }).getByText(/From the template E2E 854091 admin/)
    Expected: visible
    Timeout: 15000ms
    Error: element(s) not found
```

The error context's DOM snapshot shows the actual rendered text was a DIFFERENT sentence than the
one the test waits for:

```
- paragraph: The template E2E 854091 admin is empty, so there is nothing to copy.
```

and the board behind the dialog, at the moment of failure, is dated `Thu Sep 10 – Sat Sep 12` and
shows no shift chips anywhere in the accessibility tree (compare the same admin's board on Sep 7-9,
captured in an earlier run this week: `chips=[Shift 1 06:00-14:00 | Shift 2 14:00-22:00 | Shift 3
22:00-06:00]`).

Read `supabase/dev_demo.sql:413-456` rather than guessed: the schedule-building block loops
`FOR v_d IN 0..2 LOOP` -- three days, Monday through Wednesday of `v_day := date_trunc('week',
now())` -- and inserts runs/assignments for none of Thursday through Sunday, no matter when the
seed is (re)applied. This is not a stale-clock problem (contrast F-117, a different incident where
the clock itself was wrong): re-seeding at this exact moment, right now, on a Thursday, still only
populates Monday-Wednesday of the CURRENT week, because the loop bound is fixed at 3 regardless of
what day it runs on. Confirmed live against the tester's own database:

```
docker exec supabase_db_production_scheduler_tester psql -U postgres -d postgres -c "select
lower(timerange)::date as d, count(*) from runs where node_id in (select id from nodes where org_id
= '10000000-0000-0000-0000-000000000001') and lower(timerange) < '2026-10-01' group by 1 order by 1;"

     d      | count
------------+-------
 2026-09-07 |    12
 2026-09-08 |    12
 2026-09-09 |    12
(3 rows)
```

Twelve runs a day (3 plants x 4 cells) on Monday, Tuesday, Wednesday, and none for the rest of
September -- exactly the `v_d IN 0..2` bound, and nothing later in the seeded week at all. (Rows
dated in 2028 in the same table are `weekTemplates.spec.ts`/`copyWeek.spec.ts`'s own "apply 120
weeks out" test writes, unrelated to this defect and left there on purpose by those specs' own
design -- "a week nothing else touches.")

## Lead

Not a suspicion -- read and confirmed directly against the seed file. The three-day loop bound
(`FOR v_d IN 0..2 LOOP`, `supabase/dev_demo.sql:422`) contradicts the section's own header comment
("so no board opens empty"); the header describes an intent the loop bound does not implement.
Either widen the loop to `0..6` so the whole week carries a schedule (matching the header's own
claim), or the header's claim should say "Monday through Wednesday" instead of "no board opens
empty" and every browser spec that opens the board without navigating to a known date (this one
included) should navigate to a day inside that fixed window rather than trust "today". The first
is the smaller change and matches what the comment already promises; the second is more work
spread across every affected spec. Either way this recurs every Thursday through Sunday until
fixed, on both stacks alike -- nothing about it is specific to the tester's own database.

## Developer note

Fixed: `supabase/dev_demo.sql`'s schedule loop now runs `FOR v_d IN 0..6` (Mon-Sun) instead of
`0..2` (Mon-Wed), so no board opens empty on any day. This raises the seeded runs and assignments
from 3 plants x 4 cells x 3 days = 36 to x 7 days = 84, so the two self-checks that pin the count
moved with it: `dev_demo.sql`'s own `v_runs <> 36` and `dev_demo_test.sql`'s D6 (`v_runs = 36 AND
v_asg = 36`) are now 84/84; `v_cells` stays 12. Grepped the repo for other seed-count assumptions
and found none -- `loadSanity.spec.ts` and `copyWeek.spec.ts` read the schedule dynamically, not by
a fixed count. Not run here (a full seed needs a DB reset the maintainer's live stack must not take);
the tester's cold `--sql --e2e` is the proof.
