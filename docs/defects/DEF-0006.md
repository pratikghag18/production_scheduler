## Reproduction

`dev_demo.sql` is not run by any script — it is applied by hand after a reset,
and `db:reset` wipes the demo world every time (design-plan §19.72), so it is
run again every time. Against any database that has migrations 0043 and 0044:

```
docker exec -i -e PGPASSWORD=postgres supabase_db_production_scheduler \
  psql -U postgres -d <db> -v ON_ERROR_STOP=1 -f - < supabase/dev_demo.sql
```

I ran it against the throwaway `sql_test_db` (harness + every migration + seed),
never against the running dev database, and rebuilt the scratch database
afterwards.

Or, with no database at all:

```
npx vitest run src/test/defects/DEF-0006.test.ts
```

## Expected

R-D112: "`dev_demo.sql` clears org 1's seeded content and builds three
identically shaped plants (Plant A/B/C → Area → Line → Cell) through
`create_node`, with every row owned ... **no run using a product owned outside
it**, and one supervisor (Ana) granted a single line."

It has to reach the runs to do that.

## Lead

A suspicion, not a fact.

`supabase/dev_demo.sql:414` is the only line involved:

```sql
INSERT INTO runs (org_id, node_id, product_id, timerange, status, planned_headcount)
VALUES (..., 'planned', 1)
```

`status` has a default and the demo only ever wrote `'planned'`, so dropping the
two columns from the statement should be the whole change. The rest of the file
does not name either column — I checked, and the pin's third case asserts it.

⚠️ WHY NOTHING WENT RED. `dev_demo.sql` is on no runner's path.
`scripts/run-sql-test.sh` and `verify-db.sh` build their database from the
harness, the migrations and `seed.sql`; the vitest suite never touches SQL; and
`R-D112` has `verified_by: []`, so the one requirement that describes this file
had nothing standing behind it. Migration 0044 was careful about the four
functions and the exclusion constraint that named the column — it says so, and I
checked each by extraction — and the fixture outside the migration set was the
copy nobody grepped. That is CLAUDE.md §4's "after deleting a concept, grep the
tests for its words", with a file that is not a test.

The narrow fix is one line. The wider question, which is the developer's: whether
`dev_demo.sql` should be on a runner at all. It is the only fixture with three
plants and a line-scoped supervisor, it is what the browser sees, and it is where
every screen check this role runs starts from — including the ones that found
DEF-0002 and DEF-0005, neither of which the seed's single plant could have shown.

## Developer note

I agree with the diagnosis and the severity, and the fix is the one line the
Lead names. Two corrections to the record, neither of which lets the defect off.

⚠️ **`dev_demo.sql` IS run by a script, and that makes this worse rather than
better.** The Reproduction says it "is not run by any script — it is applied by
hand after a reset". `supabase/config.toml` has
`sql_paths = ["./seed.sql", "./dev_demo.sql"]`, and its own header block records
why that line was added: `db:reset` used to wipe the demo world and a manual
paste into Studio was the only way back. So `npm run db:reset` has been applying
this file, and failing inside it, every time — no hand step required, and no
error a person had to be watching for. The premise the defect rests on is the
narrower and correct one, which the Lead states exactly: it is on no *test*
runner's path.

**Where it stops is the part I want on the record.** The file's §8 opens with
"a demo file that half-ran is worse than one that failed" and then makes twelve
assertions — including `v_runs <> 36`, which is precisely this bug. They never
fired, because they sit at the FOOT and the file died at line 414. An assertion
block cannot catch a fixture that does not reach it, so the fixture had to go on
a runner where the APPLY itself is the test. That is what `--demo` does.

⚠️ **AND THE LIVE DEV DATABASE IS NOT BROKEN, WHICH CHANGES THE URGENCY.**
Session 55's summary says "the live dev database is already showing 0 runs
across all three plants, and dev_demo is the only thing that creates them." I
measured it: org 1 has 36 runs and 39 assignments, and FOUR roots -- Plant A, B,
C and a Plant D that is not in this fixture. The demo world was built while
`status` still existed; 0044 dropped the column and kept the 36 'planned' rows,
and `dev_demo.sql` has not been re-applied since. So nothing on this machine was
ever half-built. The breakage was always in the FUTURE tense -- the next
`db:reset` -- which is a weaker claim than the one filed and still a major
defect, because that reset was going to happen and nothing would have said why.

⛔ A CONSEQUENCE WORTH KNOWING BEFORE ANYONE RESETS: Plant D and the three
extra assignments are hand-made and live only in that database. `dev_demo.sql`
opens by deleting org 1, so the next reset takes them whether or not this fix is
in. That is the file working as designed, not a new bug, but it is the maintainer's
call and not a session's.

## Fix

`supabase/dev_demo.sql` no longer names `runs.status`.

`supabase/tests/dev_demo_test.sql` is new and is what R-D112 was missing — it
builds the demo world on a database of its own and asks it eleven questions from
outside the fixture, including the two nothing counted: the ASSIGNMENTS (the
statement immediately after the one that broke) and ANA'S SINGLE LINE.
`scripts/run-sql-test.sh --demo` builds `sql_demo_db` for it and drops it after;
it cannot share `sql_test_db`, because `dev_demo.sql` deletes org 1's seeded
content and about eighteen cases in eight files need that content intact.
`scripts/tester-run.mjs --sql` now runs it.

Measured both ways rather than assumed. With the fix: 11 passed, 0 failed, 0
hard-errors. With the bug deliberately put back: the mode exits 1 and prints the
`column "status" of relation "runs" does not exist` error verbatim. And the
eleven cases were run against the seed-only world to check they are capable of
failing at all — nine go red there, including D6 (`runs=8 assignments=12`) and
D8 (Ana's seed grant is depth 2, an Area, not depth 3, a Line); the three that
pass are invariants true of both worlds, not vacuous cases.

## Two corrections to this report, both the developer's and both right

**"It is not run by any script" was wrong.** `supabase/config.toml` carries
`sql_paths = ["./seed.sql", "./dev_demo.sql"]`, so `npm run db:reset` has been
applying this file all along. I checked the line's history: it predates this
work by many commits, so it was true when the defect was filed. The Lead's
narrower claim — on no *test* runner's path — is the accurate one, and it is
what the fix acted on.

**"The live dev database is already showing 0 runs across all three plants" was
wrong**, and it is the more serious of the two because it overstated the
urgency. I measured the database directly rather than taking the correction on
trust: org 1 holds `36 runs, 39 assignments, 4 roots`. What I had actually seen
was `board_window`'s payload for the default three-day window on one plant — the
demo's runs are dated 31 Aug to 2 Sep and today is 4 Sep, so they sit two days
behind the left edge and the board is legitimately empty. I read a windowed read
as a statement about the table. Nothing on that machine was ever half-built; the
breakage was in the future tense, on the next reset. Still major — that reset was
going to happen and nothing would have said why — but a weaker claim than the one
filed, and the record should say so.

⛔ **Seconding the developer's warning, because it is the maintainer's call and
not a session's:** the fourth root (Plant D) and three of the 39 assignments are
hand-made and live only in that database. `dev_demo.sql` opens by deleting org 1,
so the next `db:reset` takes them, fix or no fix. That is the file working as
designed; it is worth knowing before the reset, not after.
