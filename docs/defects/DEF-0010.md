## Reproduction

In the running app and against the local stack, at the committed tip `6086c23`.
The demo cast has no such person, so the first step makes one — the Access tab
does exactly this, on any node in the tree.

1. Sign in as **Admin (company)**, go to **Admin → Access**, focus **Plant A →
   Area 1 → Line 1**, and set **Ana** to **admin** there. (Or, over the company
   admin's own session: `POST /rest/v1/rpc/set_site_member`
   `{ "p_node_id": "<Line 1>", "p_profile_id": "<Ana>", "p_role": "admin" }`.)
2. Sign in as **Ana**. She now holds an admin grant on a LINE and nothing else.
3. Go to **Admin** and read the rail: Settings is there.
4. Click **Settings** and read the pane.

Then ask the server what it would have taken from her, over her own session:

```
POST /rest/v1/rpc/set_node_setting
  { "p_node_id": "<Line 1>", "p_key": "eligibility_policy", "p_value": "block" }
```

Put it back afterwards with `clear_node_setting` and set Ana back to
`supervisor`, which is what this run did.

The pin renders the same person through `SettingsPanel`'s own mocks:

```
npx vitest run src/test/defects/DEF-0010.test.tsx
```

## Expected

R-239: *"A client control is never hidden for something the server permits, and
never shown for something the server refuses."*

`SettingsPanel.tsx`'s own header describes three states, and this person reaches
none of them: their own place with working pickers, a place they may read but
not administer with no control and whose place it is, and the company scope
disabled with the reason.

`set_node_setting`'s comment (migration 0052) says what the server's answer is:

> give ONE place its own answer for ONE setting … Admin-gated by
> `app_is_admin_for` — the plant's own admin, not only the company's

and 0050's resolver says the depth is deliberate:

> `ORDER BY nlevel(anc.path) DESC` makes "nearest" mean deepest — **a line's
> override beats its plant's**.

## Lead

A suspicion, not a fact.

`canAdministerPlant` is right and is not the problem — it mirrors
`app_is_admin() or app_is_admin_for(node)` and correctly says no when it is
handed the plant root's path. The gap is one level above it, in what the tab can
be pointed AT. `SettingsScope` is `{ kind: "company" } | { kind: "plant"; … }`,
the options come from `readablePlants`, and `readablePlants` keeps only
`parentId === null`. A line grant does not make the plant root readable, so this
person's readable set has no root at all: `plants` is `[]`,
`plantControlVisible` is false, and `settingsScope`'s last line —

```ts
if (canWriteCompany) return { kind: "company" };
return plants.length === 1 ? asPlant(plants[0]) : { kind: "company" };
```

— falls to `company` for a reader it has just been told cannot write the
company. That branch's own comment reasons about two people, a company admin of
a one-plant org and a site admin granted one plant, and this is a third it was
not written for.

So the shape that suggests itself, and the developer decides: the scope is a
NODE, not a plant — the same widening the server already made in 0050 — with the
options being the reader's own `adminPaths` when they hold no readable root. What
would make that safe is already there, since `canAdministerPlant` takes a path
and does not care how deep it is.

⚠️ **The cheaper answer may be the right one and is worth putting to the
maintainer rather than assumed away.** R-333 is `stated_by: maintainer` and its
words are *"assign the settings to that particular plant"*. If an admin grant
below a plant root is not a shape this product means to support, the honest fix
is at the other end — the Access tab refuses to grant `admin` below a root, and
this person cannot exist. That is a smaller change than a node picker and closes
the same hole. What is not a judgement call is that today the Access screen
invites the grant, the server honours it, and the Settings screen has no answer
for the person it creates.

⚠️ Filed `minor` rather than `major` because it is the SAFE direction — nothing
is offered that the server would refuse, and no data is at risk. It becomes
`major` the moment the maintainer says line-level and cell-level admins are a
supported shape, because then it is a role that cannot do its job.

## Developer note

Agreed, and the maintainer chose the second of the two fixes the Lead offers:
*"the admin level should only be applied to the plant root. If you make
someone a site admin they automatically get access to the whole site and not
just to a particular hierarchy."* So the person this defect is about is one
the product no longer creates. Recorded as R-340 before any code.

**It started on the server, and that was the whole point.** Dropping `admin`
from the picker below a root would have left `set_site_member` accepting what
the screen refuses --- R-239 broken in the direction DEF-0005 and DEF-0007
both broke it. Migration 0053 re-emits the function whole with one block
added (extracted from 0021 §4, never retyped) and refuses `admin` where
`parent_id IS NOT NULL`. Measured over a real session before the client was
touched:

    admin at a plant root      -> {"role": "admin", ...}          stored
    admin one level down       -> invalid_argument, admin_below_root
    supervisor one level down  -> {"role": "supervisor", ...}     stored

`allowedRoles` then mirrors that predicate and nothing more, and the
add-someone picker reads the same list rather than `GRANT_ROLES` --- two
controls on one screen disagreeing about one rule is how this got here.

**No backfill, and the number was measured rather than assumed:** zero
below-root admin grants exist, and neither fixture makes one. An existing one
would be left alone rather than deleted, so the self-rule still returns
`["admin"]` for that row and no control is rendered with nothing selected
(case A30).

⛔ **THE PIN IS STILL RED AND I HAVE DELIBERATELY NOT TOUCHED IT.** It renders
`SettingsPanel` for a line-level admin through its own mocks, so it builds a
person the Access tab and the server now both refuse to create. This defect's
own **Reproduction** is blocked at step 1 --- `set_site_member` raises
`admin_below_root` --- which is the strongest form of fixed available and is
not something a mocked render can observe.

So the judgement is yours, and it is a real one: either the pin should assert
that the GRANT is refused rather than that the pane is right, or it should be
retired with the shape it was written for. I have not guessed, because a
developer editing a tester's pin to make it green is the one move that would
make this loop worthless.
