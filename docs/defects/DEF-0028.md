Read rather than guessed: `renderPanel` in `src/test/absenceOnBoard.test.tsx` calls React Testing
Library's `render` exactly once per case and never `rerender`s. The new case (`R-038c (F-125)`,
line ~382) is a single render with one fixed `windowStart`/`zone`/`assignmentsByOperator` triple --
it can pin that the string is built correctly THIS time, but a memo that ignores a dependency by
definition only shows a wrong answer on a SECOND render with that dependency changed and the
memoized inputs held the same. No case anywhere in the suite renders `OperatorPanel` twice with
`zone` or `windowStart` changed alone.

## Lead

A suspicion, not a fact, and it comes with a reason today's app is not actually exposed to it.
Traced `BoardPage.tsx`: `index` (`useMemo(() => buildBoardIndex(boardQuery.data, from, to,
density), [boardQuery.data, from, to, density])`, line 236) is the sole source of both
`assignmentsByOperator` and `windowStart` passed to the panel, and `zone` (line 228,
`boardQuery.data?.timezone ?? DEFAULT_TIMEZONE`) is read off the same `boardQuery.data` `index`
already depends on. So today, any real change to `zone` or `windowStart` implies a new
`boardQuery.data` and therefore a new `index.assignmentsByOperator`/`index.nodeById` identity
too -- the two dropped dependencies are currently redundant with the two that remain, which is
exactly why the mutation above changes nothing observable through `BoardPage`. That coupling is an
accident of today's wiring, not a guarantee `OperatorPanel`'s own contract states; the moment
something feeds it a `zone` or `windowStart` that can change independently of
`assignmentsByOperator`'s reference (a local override, a prop threaded around `index`), the memo
would serve a stale tooltip and nothing under `src/test/` would say so. A rerender-based case --
same `assignmentsByOperator`/`nodeById` reference, changed `windowStart` or `zone`, assert the
title output changes -- would close this without touching product code.
