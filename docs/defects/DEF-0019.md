## Reproduction

At the committed tip `19f0903`, against the local stack with 0061 applied. An
`auth.users` row with no `user_profiles` row is what a fresh sign-up is before
anyone gives it a company (`supabase/config.toml` has `enable_signup = true`,
and nothing in the schema creates a profile on sign-up — `pg_trigger` has no
row for `auth.users`). Make one inside a transaction and ask as it:

```
docker exec -i supabase_db_production_scheduler psql -U postgres -d postgres <<'SQL'
BEGIN;
insert into auth.users (id, email) values ('00000000-0000-0000-0000-00000000beef','noprofile@example.test');
select set_config('request.jwt.claim.sub','00000000-0000-0000-0000-00000000beef', true);
SET LOCAL ROLE authenticated;
select app_current_org()                                                        as org,
       resolve_shift_template('3000000b-0000-0000-0000-000000000001')          as org2_root_template,
       resolve_shift_template('1b3722c8-a85a-4682-9987-bfe0420918f1')          as org1_plant_a_template,
       app_node_exists_in_org('3000000b-0000-0000-0000-000000000001')          as exists_in_org,
       app_node_is_plant_root('3000000b-0000-0000-0000-000000000001')          as is_plant_root_0056;
ROLLBACK;
SQL
```

(`1b3722c8-…` is Plant A's id on this stack; read it with
`select id from nodes where path='plant_a'` as the owner. Pass literal uuids:
a subselect on `nodes` under the session is RLS-filtered and hands the
resolver NULL, which looks like the boundary holding.)

**The pin, which runs on every `npm run test`:**

```
npx vitest run src/test/defects/DEF-0019.test.ts
```

## Expected

R-341: a definer helper *"still answers only about the caller's own company:
for another company's node, or a uuid that exists nowhere, it gives the same
answer."* A caller with no company has no company's nodes to ask about; both
calls should answer NULL, as `app_node_exists_in_org` and
`app_node_is_plant_root` (0056, the DEF-0013 fix) answer false for the same
session. 0061's own header states the rule it means to keep: *"another
company's node, and a uuid that exists nowhere, get the same answer, nothing."*

## Actual

```
    who    | org |          org2_root_template          |        org1_plant_a_template         | exists_in_org | is_plant_root_0056
 noprofile |     | 7000000b-0000-0000-0000-000000000001 | ac127431-a4cb-4131-b632-bb8d524bf198 | f             | f
```

With `app_current_org()` NULL the WHERE clause's first predicate
(`app_current_org() IS NULL OR target.org_id = app_current_org()`) is true
and the walk is unbounded: the session reads Contoso's template id and
Northwind's. The two older helpers, asked the same thing in the same session,
say false.

For a session WITH a profile the boundary holds — as Ana the other company's
root and a bogus uuid both answer NULL (84's ST4, ST5, and re-measured here) —
so this is not DEF-0016 reopened; it is the exemption 0061 added being wider
than the owner it was added for.

⚠️ **Why `minor`.** A template id about a uuid the caller would have to guess,
for a caller who first has to exist without a company. It is filed because
0061's header claims the boundary, because the same header explains the
exemption as *"the trusted, un-tenanted path and nothing else"* when it is
also every profile-less jwt, and because the test that should have caught it
(84's ST4) runs the owner case as the superuser, where the exemption is right,
and never as an `authenticated` session whose org is null.

## Lead

A suspicion, not a fact. The exemption exists so that 30_shifts (Case 18a-c)
and 56_delete (D24) can call the resolver after `RESET ROLE`. What those cases
have in common is not that `app_current_org()` is NULL, it is that the session
is the owner. Inside a SECURITY DEFINER function `current_user` is the owner
for everybody, so 0060 §1's owner check does not transfer; but `session_user`
is still the connection's role, and every PostgREST session is `authenticated`
or `anon`. So the smallest fix keeps the body and replaces the first predicate
with something like `(session_user NOT IN ('authenticated','anon') OR
target.org_id = app_current_org())`, or drops the exemption and has the two
owner-context cases set a jwt claim before calling — which is what 84's ST4
already does to get out of owner context. Either way 84 should gain a case as
an authenticated session with no profile, expecting NULL for both companies.
If `app_resolve_node_setting` gains a boundary for DEF-0018, the same
exemption question must be answered the same way in both places.

The pin reads the last definition of `resolve_shift_template` and fails while
its text still carries `app_current_org() IS NULL`; it proves its reader by
finding the org term 0061 did add. A fix that keeps an exemption keyed on
something other than the org being null will be green; a fix that keeps this
one will not.

## Tester re-verification — 8 Sept, at `0a8da7a`

Done the way the brief asked for and last run did not: a REAL sign-up through
GoTrue (`POST /auth/v1/signup`, a fresh `tester-probe-*@example.test`
address), not a savepoint rolled back inside a psql session. GoTrue confirms
the address, hands back a real access token, and nothing in this codebase
creates a `user_profiles` row on sign-up, so this session's `app_current_org()`
is genuinely NULL while `auth.uid()` is not.

```
fresh session -> org1 Plant A date_format:  null
fresh session -> bogus node id date_format: null
fresh session -> Plant A resolve_shift_template: null
```

All three NULL: a real, un-profiled tenant session is bounded exactly like a
bogus id, for both `app_resolve_node_setting` and `resolve_shift_template`.
The probe account was deleted afterward through the admin API
(`DELETE /auth/v1/admin/users/<id>`) and confirmed gone (404 `user_not_found`)
so the local stack is left as found.

As DEF-0018 notes, this is a hand-copied predicate in `resolve_shift_template`
specifically, not a shared helper; see that defect's re-verification for the
migration-wide read. The pin has not been promoted out of `src/test/defects/`.
