## Reproduction

Tester's stack, freshly reset and seeded, the stack's values exported. Run the whole browser suite
the way `package.json` and `scripts/tester-run.mjs --e2e` do:

```
npm run e2e            (playwright test; six workers on this machine, fullyParallel)
```

Then the walk alone, the way session 194 proved it:

```
npx playwright test e2e/typedWalk.spec.ts --project=chromium --workers=1
```

## Expected

R-433: the walk "exists first as an e2e spec ... run green twice before the hand-over". A proof that
is green only when run by itself, and red under the command the repo documents for the suite, is a
proof somebody has to know how to run.

## Actual

Three runs of `npm run e2e` on 30 Sept, the walk failed in each:

```
run 1  Error: the booked Bracket A run on Cell 3, 13:00-17:00, should exist      (typedWalk.spec.ts:856)
run 2  Error: trace line 1's heard
         Expected: "clear Cell 4 2026-10-05"
         Received: "Assign Sam Patel to Housing A on Cell 1 in Line 1 from 5am to 6am 2026-10-05"
run 3  Error: the booked Bracket A run on Cell 3, 13:00-17:00, should exist
```

In all three `weekTemplates.spec.ts:145` also failed (`"afterAll" hook timeout of 30000ms exceeded`),
and in run 2 `copyWeek.spec.ts:68` (`locator.click: Timeout 15000ms exceeded`). Totals: `2 failed,
6 skipped, 44 passed`, `3 failed ... 43 passed`, `2 failed ... 44 passed`.

Alone, one worker, both sentence lists twice each over the same database: `2 passed` four times
(38.7 s, 38.3 s, 34.5 s, 34.8 s). So DEF-0042 is verified; this is what is left.

## Lead

**A suspicion, not a fact.** Two separate things in `e2e/typedWalk.spec.ts`. (1) The F-233 case
added in 96b5a37 (l.1767) is a top-level test in the same file; `playwright.config.ts` sets
`fullyParallel: true`, so it runs beside the walk, types its own sentence on the walk's day, and
writes to the same `data/voice/trace/bar.jsonl` the walk's cross-check reads line by line --
"Assign Sam Patel ... from 5am to 6am" is that case's sentence. `test.describe.configure({ mode:
"serial" })` for the file, or the F-233 case inside the walk's describe, would order them. (2) Entry
6 (the booking, l.840-858) reads `runs` once, straight after the readout; every assignment check
around it polls (`waitForAssignment`, whose own comment says why a single read is a race). Under six
workers the write had not landed. CI runs one worker with two retries, so neither shows there. The
`weekTemplates` afterAll timeout was seen by the tester on 28 Sept as well (passed alone, not filed);
it has now failed in five full runs of five and is probably load on the shared database.

## Developer note -- 30 Sept, session 195

`e2e/typedWalk.spec.ts` runs in serial order at file level (the F-233 case after the walk), the
walk's trace cross-check keeps only its own entries (typed, one of its own sentences, at or after
its start), the two booking reads poll through a new `waitForRun` beside `waitForAssignment`, and
the week-template and copy-week cases and the template cleanup hook have the room they need (22 s
alone once the target week holds an earlier run's copy; the default 30 s ran out beside five other
workers). Proved before the day's other changes: the walk alone twice per list, `npm run e2e` three
times (46 passed, 46 passed, then 45 with the week-template apply out of budget once, which is the
room added afterwards); the final three full runs are in the plan's session entry.
