## Lead

A suspicion, not a fact.

Migration 0053's own header says what it did:

> Extracted from **0021 §4** and re-emitted whole with one block added, per
> CLAUDE.md: never retype a function, and **the last definition wins.**

It quotes the rule and then breaks it in the same sentence. `set_site_member` is
defined three times and 0021 is not the last hit:

| migration | guards it raises, by `reason` |
| --------- | ----------------------------- |
| 0021 site_membership | `not found`, `not found`, `self` |
| 0022 company_admin_rows | `not found`, `not found`, **`company_admin`**, `self` |
| 0053 admin_only_at_plant_root | `not found`, `not found`, `admin_below_root`, `self` |

So the repair looks like one block, put back where 0022 had it — after "no such
person" and before the role check:

```sql
  IF app_profile_is_company_admin(p_profile_id) AND NOT app_is_admin() THEN
    PERFORM api_raise('not_permitted', 'company admins are not managed from a site',
                      jsonb_build_object('profile_id', p_profile_id,
                                         'reason', 'company_admin'));
  END IF;
```

⚠️ **The bigger question is not the block, it is that a red SQL file shipped.**
`49_company_admin_rows_test.sql` X42 fails on the committed tip. The migration's
own commit message reports `npm run test 2117 in 77, tsc 0, eslint 0` and says
nothing about the database suite, and there is no CI job standing a database up
(the queue's own e2e entry says so). Every migration in this project has a
numbered SQL file behind it and the suite is the only thing that reads them; a
migration landing without that suite being run is how a shipped rule gets
reverted by a copy-paste and nothing says a word. Whether that becomes a
pre-commit step, a CI database, or a line in the developer's checklist is the
maintainer's call, but it is the finding, and the block above is only the
symptom.

⚠️ **Worth deciding rather than assumed:** whether `remove_site_member` should be
re-emitted at the same time so the pair is written once. It is correct today by
accident — because nobody touched it — which is the same accident in the other
direction.

## Developer note

Agreed, and the lead is a fact: 0053 was copied from 0021. The cause is the
recipe rather than a slip. CLAUDE.md said `grep -n "function <name>"` and
take the last hit; 0022 declares `CREATE OR REPLACE FUNCTION
public.set_site_member`, upper case and schema-qualified, so a case-sensitive
grep for the bare name finds 0021 and 0053 only. The recipe now reads `-in`
with an optional `public.` and says why.

**0054 does not retype either.** Its body was sliced out of 0022 by a script
(from the `CREATE OR REPLACE` line to `END $function$;`), 0053's block was
inserted after the role check, and `company_admin`, `admin_below_root` and
`self` were asserted on the assembled text before the file was written.
`remove_site_member` is left where it is: re-emitting a function nothing
changed is the same risk in the other direction.

**The SQL suite ran this time, whole.** 607 passed, 0 failed, 0 hard errors
across every numbered file, X42 among them, and the demo world builds. On the
live stack as Dana, the reproduction now stops at the write:

    set_site_member(Plant A, <company admin>, 'viewer')
    -> not_permitted, reason company_admin; no row

77's AR8 asks the same question of the last definition so it cannot go quiet
again. Your pin is green, 3 of 3, untouched. On the bigger finding, that a
migration shipped with the database suite red and nothing standing in the way:
recorded as F-097 and it is a line in the checklist until the CI database
(S34's second half) exists.
