## Reproduction

Any sentence the bar turns into three or more changes where one in the middle is refused -- e.g. a
swap followed by a placement the certificate rule refuses, or a clear of a place where one removal is
refused. The developer's own case shows the wording: `npx vitest run src/test/commandBar.test.tsx -t
"CB-lot-fail-1"` (a two-change lot whose second change is refused), and the code that builds the
answer: `CommandBar.tsx` ~l.2212-2224 (the message) and `useDragGesture.ts` ~l.2842-2929 (the lot
runner).

No pin: the lot's answer is built inside `CommandBar`, whose render harness lives in
`commandBar.test.tsx` and is not exported; a pin needs a lot of three with the middle one refused
and should assert the third change is named as not done.

## Expected

R-432, as the maintainer restated it on 28 Sept: "Let the board specify what was done and what was
not done in such instances, it should be very clear and conversational message so a non-technical
person should be able to follow it." Every change is named: what was done; what was not done -- the
refused one with its reason, and every one after it that was never tried.

## Actual

The answer today, as the developer's CB-lot-fail-1 names it:

```
Did 1 of 2 things; the next failed: Tom Baker is not certified for Cell 1: missing Welding. What was already done stayed: <readout of the change that was made>.
```

The runner stops at the first failure and returns only a count and the error
(`return { done, error: err.message }`, useDragGesture.ts ~l.2923); the message is built from
`resolved.slice(0, result.done)` and that error (CommandBar.tsx ~l.2212). So in a lot of five whose
second change is refused, changes 3 to 5 are never tried and never mentioned -- the person is left
believing they may have happened. "Did 1 of 2 things; the next failed:" and the raw refusal
("...: missing Welding") are not sentences a supervisor would say (R-459).

## Lead

**A suspicion, not a fact.** The runner already knows the full list (`resolved`); the answer could
name `resolved.slice(done + 1)` as "I stopped there, so these were not done", and the refused one
in the plant's words (the same rewriting the single-sentence refusals get). CB-lot-3 and
CB-lot-fail-1 pin today's wording and will change with the fix -- the contract changed on 28 Sept,
they were not wrong when written. CLAUDE.md §7 still states R-432's old all-or-nothing form; the
developer owns that file and should restate it with this.

WHAT HOLDS. The three labelled lines are there; the database afterwards is exactly what they say
(the four done are gone, every other row is still there); the trace carries the same outcome. For a
lot on one day this is the answer the maintainer chose.

WHAT DOES NOT, and why it is reopened rather than verified: on a lot over several days -- the week
clear, the bar's largest lot -- "Not done" and "Not tried" leave the DAY out. "Maria Lopez's block on
Cell 2" is one of five; "The Housing A job on Cell 1 stays as it was, 6 am to 2 pm." is printed five
times, word for word. R-432 as restated: "what was done and what was not done ... very clear ... so a
non-technical person should be able to follow it". The Done line names each day; the other two cannot
be told apart, so the person still cannot say what the board looks like. The reason is also not the
reason: the block was gone (someone else removed it), and the answer is "You cannot change that from
here", a sentence about permission.

A suspicion: `attempted` and `notTried` are built by the resolver without the day the readout
carries; and a delete that removes no row is mapped to the not-permitted sentence whether the row is
forbidden or missing.

## Developer note -- 30 Sept, session 195

Every `attempted` and `notTried` the resolver builds now carries its day and hours the way its
readout does ("Not tried: Maria Lopez stays on Cell 2 Sat Oct 3, 2 pm to 10 pm."), so a week clear's
lines are distinct (case S195-A-1 asserts a three-day lot's sets hold three distinct strings). A
write that changed no row is read back by id as the caller (`throwIfGone`, `src/lib/api/mutations.ts`):
unreadable means "That block is no longer on the board." / "That job is no longer on the board.",
still readable stays "You cannot change that from here."; both paths go through the one rewriter
(CB-gone-1 to CB-gone-3, `writeGoneOrForbidden.test.ts` WG-1 to WG-8). The real client library's
no-rows path was proved against a scripted double, not a live refused delete.
