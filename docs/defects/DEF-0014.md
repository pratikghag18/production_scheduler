## Reproduction

At the committed tip `f75a65e`, against the local stack, as Dana
(`dana@example.test`, site admin of Plant A, org-wide `viewer`), inside a
transaction that is rolled back at the end. Take the run on Cell 1 that starts
Monday 06:00 of the demo week — it has one crew member — and move it with a
plain UPDATE of `runs.node_id` to any cell of Plant A with no run in that
window (the script picks the first one it finds):

```
docker exec -i -e PGPASSWORD=postgres supabase_db_production_scheduler psql -U postgres -d postgres <<'SQL'
BEGIN;
select set_config('request.jwt.claim.sub', (select id::text from auth.users where email='dana@example.test'), true);
SET LOCAL ROLE authenticated;
DO $$ DECLARE v_run uuid; v_from uuid; v_to uuid; v_to_path text; v_crew int; v_n int; v_run_node text; v_crew_node text; v_tr tstzrange; BEGIN
  SELECT r.id, r.node_id, r.timerange INTO v_run, v_from, v_tr FROM runs r JOIN nodes n ON n.id=r.node_id
   WHERE n.path='plant_a.area_1.line_1.cell_1' AND lower(r.timerange)='2026-08-31 06:00+00' LIMIT 1;
  SELECT count(*) INTO v_crew FROM assignments WHERE run_id=v_run;
  SELECT n.id, n.path INTO v_to, v_to_path FROM nodes n JOIN hierarchy_levels hl ON hl.id=n.level_id
   WHERE n.path <@ 'plant_a' AND hl.is_schedulable AND n.id <> v_from
     AND NOT EXISTS (SELECT 1 FROM runs x WHERE x.node_id=n.id AND x.timerange && v_tr) ORDER BY n.path LIMIT 1;
  RAISE NOTICE 'run % on cell_1 (% crew); free target: %', v_run, v_crew, v_to_path;
  UPDATE runs SET node_id = v_to WHERE id = v_run; GET DIAGNOSTICS v_n = ROW_COUNT;
  RAISE NOTICE 'raw UPDATE runs.node_id as Dana: rows=%', v_n;
  SELECT n.path INTO v_run_node FROM runs r JOIN nodes n ON n.id=r.node_id WHERE r.id=v_run;
  SELECT string_agg(DISTINCT n.path::text, ',') INTO v_crew_node FROM assignments a JOIN nodes n ON n.id=a.node_id WHERE a.run_id=v_run;
  RAISE NOTICE 'after: run on % ; its crew on %', v_run_node, v_crew_node;
END $$;
ROLLBACK;
SQL
```

`app_can_edit_node(node_id)` on both sides and she passes it.

## Expected

R-037 (`stated_by: agent`, from §15.2 and D4): *"A run moves to another cell
like any block. The target must have no overlapping run, **the crew moves
with it**, every crew member is re-checked for eligibility, and capacity is
unaffected because times do not change."*

And the schema's own standing rule for a run's crew, `assignments_run_consistency`
(0003): a crew row's cell is its run's cell. That trigger sits on the
assignments side and refuses a crew row that disagrees with its run; nothing
on the runs side refuses a run that walks away from its crew. R-345's note
in the plan says it in the developer's words: *"the table should refuse what
`move_run` would refuse."*

Migration 0058's own header names this exact door and says why `move_run`'s
pre-check is not enough on its own: *"the run row is updated first, each
assignment follows, and THIS trigger fires on that UPDATE OF node_id"* —
which is true of the crew's UPDATE and false of the run's.

## Actual

```
NOTICE:  run d80b2135-fca5-495b-af6c-c6780b8eab8a on cell_1 (1 crew); free target: plant_a.area_2.line_3.cell_5
NOTICE:  raw UPDATE runs.node_id as Dana: rows=1
NOTICE:  after: run on plant_a.area_2.line_3.cell_5 ; its crew on plant_a.area_1.line_1.cell_1
```

One row updated, no error, and afterwards the run is on Cell 5 in Area 2
while its crew member is still on Cell 1 in Area 1 — a person attached to a
run that is no longer where they are. `move_run` (0050) would have carried
the crew and re-checked each member; the table takes the bare move.

The triggers on `runs`, read off the live database: `runs_scope_guard`
(`BEFORE INSERT OR UPDATE OF node_id, product_id`, product places only),
`runs_audit`, `runs_set_updated_at`. None reads `assignments`.

⚠️ **Why `minor`.** The board never sends this statement — every move on the
screen goes through `move_run` — so it takes a hand-made PATCH over one's own
session to do it, by someone who may edit the cell anyway. No cross-plant
person results (0058's guard is on the crew's side and the crew did not
move), so R-345 holds. What is wrong is the invariant, not a permission.

⚠️ **This was found by the developer's own reviewer in session 78** and
written into the queue as the first `next` item, with the fix shape named. It
is filed here so that it is a defect with a reproduction and a red pin rather
than a paragraph, and so that R-037 — which had `verified_by: []` — has a case
on it.

## Lead

A suspicion, not a fact. The shape the queue names is the right one and the
smallest: a `BEFORE UPDATE OF node_id ON runs` trigger that refuses when the
run has crew, or carries the crew the way `move_run` does. Refusing is
simpler and matches how the assignments side already behaves
(`assignments_run_consistency` refuses rather than repairs); `move_run`
updates the run first and then each crew row, so a trigger that refuses a
run with crew would refuse `move_run` too — unless it fires only when the
statement is not `move_run`'s, or `move_run` is re-emitted to move the crew
first. Reading `move_run`'s last definition (0050) before choosing is the
whole of the work; CLAUDE.md's recipe (`grep -in "function \(public\.\)\?move_run("`,
last hit) finds it.

The pin reads the migrations: it requires some trigger on `runs` firing on an
update of `node_id` whose function names `assignments`, and it proves its
own reader by finding `assignments_run_consistency` on the other side. It
goes green on either fix shape.

## Developer note

Agreed. The lead's first shape is the fix, with the one refinement the lead
itself hints at: 0059's `runs_crew_follows` is a CONSTRAINT trigger, `AFTER
UPDATE OF node_id`, `DEFERRABLE INITIALLY DEFERRED`, so it checks at commit.
`move_run` (0050, read, not assumed) updates the run and then every crew row
inside one transaction and passes at commit; a bare PATCH is its own
transaction and is refused at its commit with `run_node_mismatch` /
`run_moved_without_crew`, naming the stranded rows. Refusing rather than
carrying, as the lead recommends and as the crew side already behaves. Six
cases in `82_run_keeps_its_crew_test.sql`, including `move_run` with crew
still passing and a `move_run` refused for another reason leaving everything
in place; the Reproduction replayed on the live database reads the refusal
and the run and crew still on cell_1.

One edit to the pin, said at the line: its trigger reader allowed only
`or replace` between `create` and `trigger`, so it could not see a constraint
trigger, which is the only correct shape here. The alternation was widened;
the claim the case makes is unchanged. Yours to judge on verification.
