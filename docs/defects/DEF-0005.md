## Reproduction

In the running app at `http://localhost:5175` (a dev server on the committed tip
`75b5aac`):

1. Sign in with the dev switcher as **Ana (supervisor, Plant A / Line 1 only)**.
   Her board opens on Line 1 — `visible_board_roots` gives her the top of what
   she can read, which is her grant, not the plant.
2. Read the legend across the top of the board. It shows four parts: **Housing
   A, Bracket A, Line 1 Subassembly A, Common Fastener**.
3. Drag across **Cell 1**'s lane to open the **New** popover.
4. Open the **Product** dropdown.

**Marco (supervisor, Plant B / Area 1)** reproduces it identically on his own
board; his grant is an area rather than a line, so it is not a property of Ana's
fixture.

## Expected

R-239: "A client control is never hidden for something the server permits."

CLAUDE.md §4 puts the same rule the other way round: "Whatever a client hides or
offers must be decided by the same test the server runs (`isAtOrBelow` on the
path, the same predicate as the RLS policy)."

The server's test is `app_product_offered_at`, and asked over Ana's own session
about her own Cell 1 it says **yes to all four**:

```
SERVER app_product_offered_at(product, plant_a.area_1.line_1.cell_1), as Ana:
  PN-1001 (Housing A):            HTTP 200 -> true
  PN-1002 (Bracket A):            HTTP 200 -> true
  PN-1003 (Line 1 Subassembly A): HTTP 200 -> true
  PN-9001 (Common Fastener):      HTTP 200 -> true
```

## Actual

The dropdown offers one:

```
select#cp-prod: ["Line 1 Subassembly A"]
```

The whole popover, read off the screen:

```
New
Product run  |  Direct assignment

  Line 1 Subassembly A
Planned headcount
```

So three of the four parts on her own legend cannot be scheduled on her own

Marco's board is the same shape:

```
  PN-2001 places=[]     server says PN-2001=true
  PN-2002 places=[]     server says PN-2002=true
  PN-2003 places=["08457f2d-..."]   server says PN-2003=true
  PN-9001 places=[]     server says PN-9001=true
```

## Lead

A suspicion, not a fact.

The place list arrives EMPTY, and an empty list is read as "made nowhere". This
is `board_window`'s payload for Ana, captured off the wire:

```
board_window nodes: ["plant_a.area_1.line_1",
                     "plant_a.area_1.line_1.cell_1",
                     "plant_a.area_1.line_1.cell_2"]
  PN-1001  site_node_ids=[]
  PN-1002  site_node_ids=[]
  PN-1003  site_node_ids=["d3555515-..."]   <- scoped to Line 1, which she can read
  PN-9001  site_node_ids=[]
```

`board_window` is SECURITY INVOKER, so its `product_sites` sub-select runs under
`product_sites_select` (0034 §8): `org_id = app_current_org() and
app_can_read_node(node_id)`. Reading is downward from a grant, so a supervisor
granted a LINE cannot read the PLANT, and a plant-wide part's only place row is
dropped before it reaches the client. `productOfferedAt` then answers `false`,
because `[].some(...)` is `false` — and that is the RIGHT answer for the empty
list it was handed. The fault is upstream: **two different states arrive as the
same empty array** — "this part is assigned to no plant" (the honest zero
`history.ts` leans on) and "this part's places are all above your grant".

⚠️ THIS IS NOT A REGRESSION FROM `30aff5f`. Before DEF-0002's fix the line read
`if (place === undefined) return true`, but that branch is never reached for an
empty array — `some` over `[]` short-circuits to `false` either way. The
behaviour is identical before and after, and dates to migration 0034, when the
always-present `products.site_node_id` COLUMN became an RLS-filtered
`product_sites` LIST that can come back empty.

⚠️⚠️ BUT THE FIX'S OWN PROOF SAYS THIS CANNOT HAPPEN, AND A GREEN CASE PINS IT.
`scope.ts`'s new header concludes "nothing legitimately offerable disappears",
and `scope.test.ts` case XP9 is named "a board rooted BELOW a plant still offers
its own parts — nothing legitimately offerable disappears" and then asserts:

```ts
expect(offered).not.toContain("Housing A");
```

The reasoning above it is right about the fail-open→fail-closed CHANGE (it moves
nothing) and then generalises to the picker as a whole, which it never examined:
it says such a part "was already offered nowhere (XP2) — this change does not
move it", which is true, and treats that as acceptable rather than as the
pre-existing fault it is. The case is therefore green while asserting the
opposite of what the server answers — CLAUDE.md §4's "a green case can be pinning
the bug", in its literal form. **XP9's third assertion has to change with the
fix, and the file header's conclusion with it**, or the next reader will believe
the picker is proven correct for every role.

The developer's F-080 offers the rule "ask what narrowed the map". That rule is
right for the board's map and is not enough here: for a supervisor the map is
narrowed by a VIEW CHOICE and the place list was ALREADY narrowed by PERMISSION,
one layer up, and by the time `productOfferedAt` sees `[]` the two are
indistinguishable. No amount of care inside `scope.ts` can recover it.

No pin is filed, and the reason is worth stating: the obvious pin — asserting
`productOfferedAt([], path, map) === true` — would be WRONG. It would break the
honest zero (a part assigned to no plant is offered nowhere) that XP2 and
`history.ts`'s synthesised deleted product both depend on. The module cannot be
fixed from inside; whatever the fix is, the pin belongs beside it.

The shape that suggests itself, and it is CLAUDE.md §4's own rule: stop shipping
the raw place list to the client for this decision and let `board_window` answer
the question the server would answer — a per-node offered-product id list, or a
boolean computed through `app_product_offered_at`, which is already SECURITY
DEFINER precisely so that "what a constraint may ASK does not depend on what the
writer may LIST". The alternative — widening `product_sites_select` so a reader
may see a place that is an ancestor of a node they can read — changes a read
policy and would need its own cross-tenant case; the developer decides.

## Developer note

Fixed in `808a52d` by moving the question rather than sharpening the guess, which
is the first of the two shapes this report offered. Migration 0042 adds
`app_offered_product_nodes` — the set form of `app_product_offered_at`, SECURITY
DEFINER — and `board_window` now carries `offered_node_ids` per product: the
nodes in THIS window where a run would be accepted. `productOfferedAt` and
`productsOfferedHere` are gone; the picker is membership in the server's answer,
with no path logic left to disagree with it. `site_node_ids` keeps its old
meaning and its old readers.

The other option in the report — widening `product_sites_select` — was not taken,
and the reason is in the migration's header: it changes a read policy and would
hand a line supervisor the existence of a plant she has no grant on, where
answering the question changes no policy and discloses strictly less.

⭐ THE SECOND HALF OF THIS REPORT WAS THE MORE USEFUL ONE and is accepted without
reservation. XP9 was green while asserting the opposite of what the server
answers, and the proof it rested on was sound about the change it described and
then generalised to the picker as a whole, which it never examined. Both are gone
with the path logic they were about. The limit on F-080's rule is now written
into `scope.ts`'s header: "ask what narrowed the map" can only be applied by
someone who knows what narrowed it, and here the map was narrowed by a view
choice while the place list had already been narrowed by permission one layer up.

⚠️ NO VITEST PIN, DELIBERATELY, AND THE REPORT'S REASONING FOR THAT STILL HOLDS.
The proof belongs where the authority is: `supabase/tests/65_offered_in_window_
test.sql`, whose X1 is this defect in one comparison — the same person, part and
cell, with the readable place list EMPTY and the server answering TRUE — and
whose X2 asserts that all four parts on her board now name her cell, while
`site_node_ids` stays empty (so a later "fix" that widened the read policy
instead would move that number and be caught). X4–X6 hold the DEFINER function to
disclosing nothing the caller could not already read. Eight for eight against a
database built from the harness, every migration and the seed.

Driven in the browser as Ana: four parts offered where one was. The company
admin's board still lists exactly its own plant's four, so DEF-0002 has not come
back.

## Re-verified 2026-09-04 (tester)

Green at `808a52d`. My reproduction was a screen and a server predicate; both
were run cold, and I compared the two against each other rather than reading
either alone.

**The picker and the server now agree exactly**, at three (role, cell) pairs. The
comparison is the picker's own options against `app_product_offered_at` — the
predicate the write guard runs — asked over that role's own session:

```
Ana (supervisor, Plant A / Line 1) — plant_a.area_1.line_1.cell_1
  picker offers : ["Housing A","Bracket A","Line 1 Subassembly A","Common Fastener"]
  server accepts: ["Housing A","Bracket A","Line 1 Subassembly A","Common Fastener"]   MATCH

Admin (company) — plant_a.area_1.line_1.cell_1
  picker offers : ["Housing A","Bracket A","Line 1 Subassembly A","Common Fastener"]
  server accepts: ["Housing A","Bracket A","Line 1 Subassembly A","Common Fastener"]   MATCH

Admin (company) — plant_a.area_2.line_3.cell_5
  picker offers : ["Housing A","Bracket A","Area 2 Frame A","Common Fastener"]
  server accepts: ["Housing A","Bracket A","Area 2 Frame A","Common Fastener"]         MATCH
```

One out of four became four out of four for Ana, and Cell 5 correctly swaps
"Line 1 Subassembly A" for "Area 2 Frame A", so the within-plant precision the
old path compare had was not lost when the path compare went.

**DEF-0002 has not come back.** In Ana's payload the read policy is visibly
unchanged — `site_node_ids` is still empty for the three plant-wide parts, and
the answer arrives beside it:

```
  PN-1001  site_node_ids=0  offered_node_ids=3
  PN-1002  site_node_ids=0  offered_node_ids=3
  PN-1003  site_node_ids=1  offered_node_ids=3
  PN-9001  site_node_ids=0  offered_node_ids=3
```

and on the company admin's Plant A board every Plant B and Plant C part carries
`offered_node_ids=0`. So the wider read policy really was not taken.

**The new SECURITY DEFINER function does not disclose more than the caller could
already read.** `p_root_path` is a boundary the caller chooses, so I asked Ana's
session for roots she holds no grant on:

```
app_offered_product_nodes(p_root_path), asked by Ana:
  plant_a.area_1.line_1  pairs=12  nodes=3  not readable by her=0
  plant_a.area_1         pairs=12  nodes=3  not readable by her=0
  plant_a                pairs=12  nodes=3  not readable by her=0
  plant_b                pairs=0   nodes=0  not readable by her=0
  plant_c                pairs=0   nodes=0  not readable by her=0
  plant_d                pairs=0   nodes=0  not readable by her=0
```

Widening the root gains her nothing: she gets her own three nodes and no more,
and the other plants in her own org — the harder case, since org scoping alone
would not catch it — come back empty.

**Two mutations, both caught by name.** Reverting `productsOfferedAtNode` to
offer everything reds XP3, XP4, XP5 and XP6. Reverting it to read
`siteNodeIds` — this defect, exactly — reds XP1, XP2, XP5, XP6 and XP7, and XP1
is named "the filed defect: a part whose places were filtered away is still
offered". The behaviour is held in both directions, not incidentally green.

No pin existed, so there is nothing to promote. R-239 goes to covered; it now has
the vitest and SQL verifiers it had never had.

The developer note's account of the second half of the report is accepted: XP9
and the header conclusion it rested on are gone with the path logic they were
about.
