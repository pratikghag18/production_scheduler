## Reproduction

With the tester's own stack up (`node scripts/tester-stack.mjs up`) and NOTHING exported by hand
(a clean shell -- `tester-run.mjs` sets the env itself from `tester-stack.json`):

```
node scripts/tester-run.mjs
```

or, to isolate it from the rest of the run:

```
node scripts/tester-stack.mjs up
node scripts/tester-run.mjs --sql --e2e
```

Both fail on the same case, every time. By contrast, a plain `npx vitest run` in a shell with none
of the tester's variables set (no `tester-run.mjs` involved) passes all 2667.

## Expected

R-366's own `verified_by` lists `src/test/testerStack.test.ts` TS9-TS10 as proof that "no e2e spec
names a stack port by literal" and that `e2e/env.ts`'s `mailUrl` "follows `E2E_MAIL_URL`, and
defaults to the developer's inbucket." A pin offered as proof of an isolation guarantee ought to be
green precisely when that isolation is in effect -- the tester's own stack, run the way `tester.md`
says to run it (`node scripts/tester-run.mjs --sql --e2e`, "do that at least once per session"). The
vitest total is also supposed to equal the plan's newest confirmed session exactly (2667) on every
run this brief describes.

## Actual

```
 ❯ src/test/testerStack.test.ts (10 tests | 1 failed) 15ms
   × TS10 / DEF-0026: e2e/env.ts's mailUrl follows E2E_MAIL_URL, and defaults to the developer's inbucket 6ms

 Test Files  1 failed | 130 passed (131)
      Tests  1 failed | 2666 passed (2667)

 FAIL  src/test/testerStack.test.ts > R-366: the tester's config.toml is generated, never shared > TS10 / DEF-0026: e2e/env.ts's mailUrl follows E2E_MAIL_URL, and defaults to the developer's inbucket
AssertionError: expected 'http://127.0.0.1:54424' not to be 'http://127.0.0.1:54424' // Object.is equality
```

Reproduced twice: once inheriting variables I had exported by hand from `tester-stack.mjs up`'s own
printed block, and again from a completely clean shell where `tester-run.mjs` set them itself from
`tester-stack.json` -- same failure, same message, both times. A plain `npx vitest run` with no
tester variables present passes 2667/2667, so the trigger is specifically "vitest launched with
`E2E_MAIL_URL` already set to the tester's own value in the real environment," which is exactly the
condition `tester-run.mjs` creates on purpose (`scripts/tester-run.mjs`'s own comment: "`run()`
below hands every child process `process.env` as-is ... so setting it here is enough for the SQL
runs and `npm run e2e` alike to inherit it" -- vitest is handed the same, unfiltered `process.env`).

Read the test itself (`src/test/testerStack.test.ts:91-102`):

```
it("TS10 / DEF-0026: e2e/env.ts's mailUrl follows E2E_MAIL_URL, and defaults to the developer's inbucket", async () => {
  vi.stubEnv("E2E_MAIL_URL", "http://127.0.0.1:54424");
  vi.resetModules();
  const withKnob = await import("../../e2e/env");
  expect(withKnob.mailUrl).toBe("http://127.0.0.1:54424");
  vi.unstubAllEnvs();
  vi.resetModules();
  const fallback = await import("../../e2e/env");
  // `.env.local` may or may not carry the knob on a given machine; either the
  // developer's default or whatever that file says, never the tester's.
  expect(fallback.mailUrl).not.toBe("http://127.0.0.1:54424");
});
```

`vi.unstubAllEnvs()` only removes vitest's own stub overlay; it does not, and cannot, erase a
variable that was genuinely present in `process.env` before the vitest process ever started. When
`tester-run.mjs` sets `process.env.E2E_MAIL_URL` (its `setUnlessPresent("E2E_MAIL_URL",
stack.mailUrl)`) and then spawns vitest with that same `process.env`, the "fallback" half of TS10
is reading the real ambient value, not the developer's default -- and that real value is, by
construction, the tester's own mail port. The comment on the test's last line already names the
one case it does not handle ("never the tester's"), which is exactly the case `tester-run.mjs`
creates.

## Lead

A suspicion, not a fact. TS10's first half (the explicit stub) is sound and adds nothing this
finding doubts. Its second half is testing "what does a shell with no `E2E_MAIL_URL` opinion see,"
which is not a state `vi.unstubAllEnvs()` can produce once the real process already had one set --
the test would need to save and delete `process.env.E2E_MAIL_URL` directly (not through
`vi.stubEnv`) and restore it afterward, the way one would guard any test that depends on an
ambient variable a wrapping script also sets. Whether that is worth fixing given the "it works
either way" of R-366's other witnesses (TS1-9, the manual proof, and the two specs' own live pass)
is the developer's call -- the count still has to come out to 2667 clean on a tester run, so this
is not a "nothing is wrong" lead the way the two left in session 115/116 were.
