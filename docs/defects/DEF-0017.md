## Reproduction

At the committed tip `aca40d5`, against the local stack. Plant A carries a
per-plant date format (`node_settings`: `plant_a / date_format / ymd_slash`);
the company default is `d_mon_yyyy`. In the browser at
`http://localhost:5173`, week `2026-08-31`:

1. As Dana (site admin, Plant A): the day header reads `Mon 2026/08/31`, the
   toolbar `Mon 2026/08/31 – Wed 2026/09/02`.
2. As Ana (supervisor, Line 1 of Plant A): the day header reads `Mon Aug 31`,
   the toolbar `Mon Aug 31 – Wed Sep 2`, the chip pop-up `Mon Aug 31`.

The server's own answer for her line, as her:

```
select app_resolve_node_setting((select id from nodes where path='plant_a.area_1.line_1'), 'date_format');
```

**The pin, which runs on every `npm run test`:**

```
npx vitest run src/test/defects/DEF-0017.test.ts
```

## Expected

R-333 (`stated_by: maintainer`): *"Every setting the tab surfaces is per-plant
— the date format as well as the eligibility policy — each with the same three
states (inheriting / set here / set here to the other value)."* And its rider:
*"A screen genuinely showing more than one plant uses the COMPANY default"* —
Ana's board shows one line of one plant, so it uses that plant's value. The
server agrees: `app_resolve_node_setting(line_1, 'date_format')` walks the
ancestry and is SECURITY DEFINER, so it answers `ymd_slash` for Ana as it does
for Dana.

⚠️ **Why `minor`.** Dates are still correct, only their shape differs from the

It is filed because R-333 was a decision the maintainer made explicitly, and
the board of the plant's own supervisor is the screen it was made for.

## Lead

A suspicion, not a fact. `useDateFormat(enabled, plantNodeId)` in
`src/features/admin/hooks/useOrgSettings.ts` takes the board's root node id
and answers `ownOverride(overrides.data, plantNodeId) ?? company` — the root
node's OWN `node_settings` row, or the company value. For a board rooted at a
plant that is the plant's row; for a board rooted at a line it is the line's
row, which does not exist, and the plant's row above the grant is not readable
by her (`node_settings` read policy) even if the hook walked up. The server
already has the resolved answer in a SECURITY DEFINER function granted to
`authenticated`; `board_window` already sends the resolved
`eligibility_policy` per node in `node_policies` (R-331). The smallest fix is
to carry the resolved `date_format` for the root the same way — in
`board_window`'s payload, or through one RPC call to
`app_resolve_node_setting` — and have `BoardPage` read that instead of the
root's own override.

The pin reads the source: `useDateFormat`'s body must not decide a node's
format from the node's own override alone; it passes if the hook (or the API
it calls) asks a server resolver, or if the last `board_window` definition
emits a resolved `date_format`.

## Developer note

Agreed, and the lead's first shape is the fix. 0062 re-emits `board_window`
whole from 0058 with one key added beside `can_place`: `date_format`, the
value `app_resolve_node_setting` reaches for the board's root, coalesced to
the client's default so the payload never carries null. The board reads the
payload and no longer asks the hook for the root's own row; a payload without
the key is refused rather than guessed at. Four cases in
`85_board_date_format_test.sql`, the API file's key check learns the one
string the payload carries, the pin green, and the Reproduction replayed
live: Ana's board window carries `ymd_slash`, and her header reads
`Mon 2026/08/31 – Wed 2026/09/02`, the same as Dana's. The role walk asserts
the two headers share a format.
