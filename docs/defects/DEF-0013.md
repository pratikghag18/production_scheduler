## Expected

R-341 (`stated_by: agent`, written for this defect from the schema's own
standing rule): *"A SECURITY DEFINER helper answers nothing about a node outside
the caller's org: for another company's node, or one that does not exist, it
gives the same answer."*

That rule is not new; it is what 0020 wrote on the helper 0054 says it copied:

> `app_node_exists_in_org` … *Does this node exist in the caller's org,
> regardless of whether the caller can SEE it? … it grants nothing and is
> org-scoped, so it says nothing about another tenant.*

And 0054's own header, describing the new helper:

> `app_node_is_plant_root` is SECURITY DEFINER **in the shape of
> `app_node_exists_in_org` (0020)**

The suite says the same thing of every definer helper it has looked at: 65's
X4–X6 — *"the SECURITY DEFINER helper discloses nothing the caller could not
already read — not a root above their grant, not a sibling department, not the
other tenant"* — and session 73's adversarial pass recorded of `set_node_setting`
that *"the other tenant's plant root is indistinguishable from a bogus uuid —
both 'no such place in this company', which discloses nothing."*

⚠️ **Why `minor` and not more.** What leaks is one bit — *this uuid is a plant
root somewhere* — and only about a uuid the caller already holds; node ids are
random v4 and nothing in this app hands another company's ids out. Nobody's rows
are readable and nothing can be written. It is filed because the schema has a
stated standard for definer helpers, the migration claims to meet it, and the
suite that proves it elsewhere (65, 80) has no case on this helper.

⚠️ **What is NOT wrong.** Everything else the trigger does was pushed and held:
the company admin is bound (`P1 … state=PT400 rows_after=0`), the service role
cannot reach the table at all (`P2 … permission denied for table profile_grants`),
the owner exemption is exactly what the header says and nothing an RPC can reach
(`set_site_member` is SECURITY INVOKER and is the only writer), `anon` cannot
call the helper (`P10 … permission denied for function app_node_is_plant_root`),
and the RPC itself says *"no such node"* for a foreign leaf before the trigger is
ever reached (`P11`).

## Lead

A suspicion, not a fact. The migration header already contains the reasoning
that leads here — the helper is definer so *"whether the caller can SEE the
node never decides an answer about the node's shape"* — and org membership is
not visibility. 0020's helper is the one-term difference:

```sql
  SELECT EXISTS (
    SELECT 1 FROM nodes n
     WHERE n.id = p_node_id AND n.parent_id IS NULL
       AND n.org_id = app_current_org()
  );
```

With that term a foreign root is "not a root here", so the trigger refuses it
with `admin_below_root` — the same answer as a bogus uuid — and the policy never
gets to speak. That changes P5's SQLSTATE from 42501 to PT400 and nothing else:
47's W28 is a root in the SAME org and stays with the policy, and every AR case
is in-org. Worth a tenth case in 77 that asks the question of the helper
directly, the way 65's X4–X6 ask it of theirs, so a later re-emission cannot
drop the term the way 0053 dropped 0022's guard.

Making the helper SECURITY INVOKER instead is the wrong repair, and the
migration header already measured why (W28). The pin's third case says so.
