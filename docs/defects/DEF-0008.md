## Lead

A suspicion, not a fact.

The gap is not in `adminSectionsFor`; it is that the rail has three populations
and the suite only ever renders two of them against the tab list. `auditAccess`
renders a company admin and a site admin. `adminNoGrants` renders a supervisor
but asks about panels, not buttons. `requireAdmin` renders a supervisor but asks
about the door, not the rail. So the third population — admitted, but narrowed —
has no case that names the set it gets.

The cheapest close is the assertion shape, not more cases: assert the WHOLE
LIST of rail buttons rather than three `toBeTruthy()`s, because a list cannot be
widened quietly and three truthy checks can. `src/test/defects/DEF-0008.test.tsx`
does that and is green on this build — it is red on the one-line mutation above,
which is the only sense in which a pin for a coverage hole can be red. Promoting
it probably belongs beside `adminNoGrants.test.tsx`, which already owns "what a
supervisor gets on the admin screen", rather than in `auditAccess.test.tsx`,
which is about one tab.

⚠️ Worth deciding rather than assuming: whether `adminSectionsFor`'s three-item
array should also be asserted directly as a unit, in `session.ts`'s own suite.
The rail case above covers the same ground through the screen, which is where a
person would see it; a unit case would be a second copy of the same list, and
CLAUDE.md §4 has a line about column lists that appear twice. The developer
decides which one is the record.
