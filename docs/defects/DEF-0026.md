## Reproduction

At tip `09a3ea4`, with the tester's own stack up (`node scripts/tester-stack.mjs up`, then
exported per `tester.md`):

```
node scripts/tester-run.mjs --sql --e2e
```

or directly:

```
npx playwright test e2e/invite.spec.ts e2e/passwordReset.spec.ts
```

## Expected

R-366: *"The tester worktree runs its Playwright suite against a dev server on a port of its own
and a Supabase stack of its own --- its own containers, its own ports, its own data --- so a
developer session hot-editing this folder, or seeding a fixture into the developer's database,
cannot change what a tester run sees."* A tester run's own emails (an invite, a password reset)
must arrive in the tester's own mail catcher and be found there --- the same isolation R-366
already gives the Vite port and the Supabase API/DB, extended to the one other per-stack service
these two specs depend on.

## Actual

```
  1) [chromium] › e2e\invite.spec.ts:164:1 › an admin invites by email; the person sets a password and lands with their grant

    Error: No invite email arrived for invitee-1788990605676@example.test within 15s

  2) [chromium] › e2e\invite.spec.ts:222:1 › a refused grant on a fresh invite leaves no orphan: the address invites afresh and gets mail

    Error: No invite email arrived for orphan-1788990606079@example.test within 15s

  3) [chromium] › e2e\passwordReset.spec.ts:135:1 › a forgotten password is reset by email and the new one works

    Error: No reset email arrived for reset-1788990609190@example.test within 15s

  4) [chromium] › e2e\passwordReset.spec.ts:202:1 › the emailed reset link lands on the reset screen, not the board

    Error: No reset email arrived for link-... within 15s

  5) [chromium] › e2e\passwordReset.spec.ts:301:1 › a recovery session dropped on the board's URL is sent to the reset screen

    Error: No reset email arrived for reset-root-... within 15s

  5 failed
  39 passed (1.2m)
```

Every case in both files that follows a real email fails, deterministically -- not a flake, and
not one seen among the passing 39.

Read both files rather than guessed: both hard-code
```
const MAIL_BASE = "http://127.0.0.1:54324";
```
`54324` is the DEVELOPER's `[inbucket] port` (`supabase/config.toml:79`). The tester's own
generated config (`scripts/lib/testerStack.mjs`'s `port`/`shadow_port` shift, +100) carries
`[inbucket] port = 54424` (`C:\dev\scheduler-test-stack\supabase\config.toml:79`, confirmed by
reading the file directly). The tester's own Supabase auth service sends the invite/reset email
into ITS OWN inbucket at 54424; `fetchInviteLink`/`fetchResetLink` poll 54324 for 15 seconds,
find nothing, and time out. The email was sent and delivered correctly -- to the right mailbox on
the wrong stack, which is R-366's own isolation guarantee failing in the one direction nobody
measured.

Confirmed this is not a general env-wiring gap in these files: `invite.spec.ts`'s own
`FUNCTIONS_BASE` is built from `supabaseUrl` (`e2e/env.ts`, which already tracks the tester's
stack correctly) two lines above the hard-coded `MAIL_BASE` --- the file already knows how to
derive a per-stack URL and did it for one service, not the other.

## Lead

A suspicion, not a fact. `e2e/env.ts` exports `e2ePort`/`e2eBaseUrl` (R-366's own port knob) but
has no equivalent for the mail catcher; `MAIL_BASE` in both specs would need the same treatment.
The tester's inbucket port is a fixed +3 offset from the Supabase API port on both stacks today
(54321->54324, 54421->54424) if that relationship is meant to hold generally, or
`scripts/tester-stack.mjs env` could print a `VITE_SUPABASE_MAIL_URL`-shaped value the way it
already prints `VITE_SUPABASE_URL`/`E2E_PORT`, read here the same way `supabaseUrl` is. Either
fix belongs in `e2e/env.ts` so it is computed once, not per spec -- the exact shape CLAUDE.md
section 4 and this file's own header warn about ("a list that appears twice is a bug with a
delay on it").
