## Reproduction

At tip `8d5eb26`. Read `docs/plan.yaml`'s R-359 row, `verified_by` entry for
`src/test/absence.test.ts`:

> "the three BOUNDARY cases, each mirrored in 88_absences_test.sql by the name
> it carries there (AB23 a shift starting exactly when the absence ends, AB24
> a shift ending exactly when it starts, and the existing case for a shift
> starting exactly when the absence starts, which does clash)"

Then read `supabase/tests/88_absences_test.sql`'s header block (AB0-AB25) and
grep the whole file for a case testing a shift **starting exactly when a
part-day absence starts**, expecting a clash:

```
grep -n "09:00" supabase/tests/88_absences_test.sql
```

## Expected

The claim says all three client boundary cases are "each mirrored in
88_absences_test.sql by the name it carries there." This is the exact
sentence DEF-0022 was filed and fixed to correct, for a different pair of
cases (AB15/AB16 wrongly claimed to carry AB23/AB24's names before they
existed). The corrected sentence should not repeat the same shape of claim
for a case that still has no SQL counterpart.

## Actual

AB23 and AB24 exist and do mirror their client cases by name. The third case
named in the claim -- "a shift starting exactly when the absence starts, which
does clash" (`src/test/absence.test.ts` line 150, unnamed by an ABnn tag) --
has no counterpart anywhere in `88_absences_test.sql`. AB15 tests a clash with
a shift well inside the absence's hours (10:00-12:00 against a 09:00-13:00
absence), not touching the exact starting instant, and no other AB case uses
a window starting at 09:00 expecting `absent: true`. The parenthetical's claim
that this case, too, is "mirrored...by the name it carries there" is false:
it carries no name in the SQL file because it isn't there.

I checked whether this is a live coverage gap, the way DEF-0022 was, by
mutating the stored absence range to fully open (`'[)' ` to `'()'`, so the
absence's own start becomes exclusive) and rebuilding the scratch database:
every one of `88_absences_test.sql`'s 30 cases stayed green. Then I probed the
live mutated server directly for the exact scenario the claim describes:

```
set_absence(operator, '2027-08-01','2027-08-01','probe',NULL,'09:00Z','13:00Z')
absence_overlap(operator, tstzrange('09:00Z','10:00Z'))
-> {"absent": true}   (still correct even under the mutation)
```

So this is not a live risk the way DEF-0022's boundary was: any placement
window with real duration starting at or after an absence's start overlaps
the absence's interior regardless of whether the absence's own start is
inclusive or exclusive, so the exact clause the claim names cannot be made to
answer wrongly by a boundary-type mutation, and AB15 already proves the
general "overlapping shift clashes" behaviour. The defect is narrowly in the
plan's own record: it names a specific SQL mirror that does not exist.

## Lead

A suspicion, not a fact. The lane that wrote AB23-AB25 (see
`docs/agent-briefs/def-0022-the-suite-must-be-able-to-fail-brief.md`) was told
to mirror the client's boundary `it` titles by name and did so for two of the
three; the third slipped through into the plan's prose without a matching
case being added, most likely because it was already believed proven by AB15.
The smallest fix is wording: drop the parenthetical's "mirrored...by the name
it carries there" for the third case, or say plainly that it rests on AB15 by
a different name and value. Adding a genuinely new AB26 for it would not add
coverage, since no window with positive duration can distinguish an inclusive
from an exclusive absence-start in this comparison; if a case is added anyway
for symmetry, its non-boundary-sensitivity should be said in the case itself
so a future reader does not mistake it for a fourth thing DEF-0022 secured.
