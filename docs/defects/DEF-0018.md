## Reproduction

At the committed tip `19f0903`, against the local stack. Give the OTHER
company's plant root a date format and an eligibility policy as the owner, then
ask the resolver about it as Ana (`ana@example.test`, org 1, a supervisor
granted Line 1 of Plant A and nothing else — the least-privileged signed-in
person the demo has):

```
docker exec -i supabase_db_production_scheduler psql -U postgres -d postgres <<'SQL'
BEGIN;
insert into node_settings (org_id, node_id, key, value) values
  ('10000000-0000-0000-0000-000000000002','3000000b-0000-0000-0000-000000000001','date_format','iso'),
  ('10000000-0000-0000-0000-000000000002','3000000b-0000-0000-0000-000000000001','eligibility_policy','block');
select set_config('request.jwt.claim.sub','00000000-0000-0000-0000-0000000000a2', true);
SET LOCAL ROLE authenticated;
select app_resolve_node_setting('3000000b-0000-0000-0000-000000000001','date_format')       as other_org_date_format,
       app_resolve_node_setting('3000000b-0000-0000-0000-000000000001','eligibility_policy') as other_org_policy,
       app_resolve_node_setting('3000000b-0000-0000-0000-000000000002','eligibility_policy') as other_org_leaf_inherits,
       app_resolve_node_setting('ffffffff-ffff-4fff-8fff-ffffffffffff','date_format')       as bogus,
       app_node_exists_in_org('3000000b-0000-0000-0000-000000000001')                        as exists_in_org;
ROLLBACK;
SQL
```

The same over PostgREST as Ana is `POST /rest/v1/rpc/app_resolve_node_setting`
with `{"p_node_id":"3000000b-0000-0000-0000-000000000001","p_key":"date_format"}`;
the function is granted to `authenticated` (`has_function_privilege` = t) and
not to `anon`.

**The pin, which runs on every `npm run test`:**

```
npx vitest run src/test/defects/DEF-0018.test.ts
```

## Expected

R-341 (`stated_by: agent`, from 0020 §8.0, 0054 and DEF-0013): *"A helper
that runs as its definer so the caller's row-level view cannot get in the way
still answers only about the caller's own company: for another company's node,
or a uuid that exists nowhere, it gives the same answer."* Both calls for the
other company's root should answer what the bogus uuid answers — NULL — and
agree with `app_node_exists_in_org`, which says false for the same uuid.

## Actual

```
 who | other_org_date_format | other_org_policy | other_org_leaf_inherits | bogus | exists_in_org
 ana | iso                   | block            | block                   |       | f
```

Ana reads the other company's chosen date format, its eligibility policy, and
the policy its leaf inherits, by uuid. `app_node_exists_in_org` says the node
does not exist for her. A signed-in session with no profile row at all
(`app_current_org()` NULL) gets the same `iso`.

⚠️ **Why `minor`.** One setting value about a uuid the caller already holds;
nothing is written and nothing grants access. It is the same size as
DEF-0013, and it is filed for the same reason: it is the bit every other
definer helper here is written not to give, and the helper's own header
(0050 §3) presents it as the settings twin of `app_node_exists_in_org`.

⚠️ **Older than this diff, and more load-bearing after it.** The function is
0050's and has read this way since 4 Sept; 0061's own header says so in so
many words (*"app_resolve_node_setting (0050) sidesteps this by never reading
app_current_org() at all, but it also carries no boundary"*) and then bounds
the shift resolver and leaves this one. 0062 makes it the authority for every
board's date format, so it is now called on every board load.

## Lead

A suspicion, not a fact. The last definition (0050, no later hit) is:

```
SELECT COALESCE(
  (SELECT ns.value FROM nodes target
     JOIN nodes anc ON target.path <@ anc.path AND anc.org_id = target.org_id
     JOIN node_settings ns ON ns.node_id = anc.id AND ns.key = p_key
    WHERE target.id = p_node_id ORDER BY nlevel(anc.path) DESC LIMIT 1),
  (SELECT o.settings->>p_key FROM nodes n JOIN orgs o ON o.id = n.org_id WHERE n.id = p_node_id));
```

Neither branch names the caller's company. The smallest fix is 0056's: put
`target.org_id = app_current_org()` (and `n.org_id = app_current_org()` on the
company branch) on the target scan, extracted from 0020 rather than retyped.
The owner-context question 0061 met will come up here too — `check_eligibility`
and `board_window` are exercised as the superuser in several SQL files — and
0061's answer (`app_current_org() IS NULL OR ...`) is the one DEF-0019 is
filed against, so the honest exemption is the session role, not the org being
null: inside a definer `current_user` is the owner, but `session_user` is
still the connection's role, and a PostgREST caller is always `authenticated`
or `anon`. Whichever shape is chosen, 74's N7 and 85's B1 must stay green as
Ana, and a case as the other tenant should be added to 73 or 85.

The pin reads the migrations: the last definition of
`app_resolve_node_setting` must carry an `app_current_org()` term, and the
reader proves itself on `app_node_exists_in_org`'s.

## Update, 7 Sept (tester)

Migration 0063 (plant-local time) adds a third key, `timezone`, resolved
through this same function and now carried on every board load beside
`date_format`. Confirmed live: the other company's root, given a `timezone`
override, answers `America/Chicago` to Ana by literal uuid the same way it
answers a `date_format`, while `app_node_exists_in_org` says false for the
same uuid. Not a new defect -- `p_key` is generic, so any key this function
is asked to resolve is exposed the same way -- but the blast radius named in
the title ("another company's plant settings") now explicitly includes the
zone as well as the date format and the eligibility policy. `board_window`
itself is not the path in: it only ever hands the resolver a node id it has
already confirmed is in the caller's own org via `scoped_nodes`, the same
protective indirection 0062 used for `date_format`, so this is about the bare
RPC (`POST /rest/v1/rpc/app_resolve_node_setting`), not the board payload.

## Tester re-verification — 8 Sept, at `0a8da7a`

Live, not a rolled-back transaction: signed in as `ana@example.test` for real
(`POST /auth/v1/token?grant_type=password`), then `POST

```

Ana -> her own Plant A date_format (sanity): "ymd_slash"
```

The other company's root and a uuid that exists nowhere now answer the same
thing (`null`), and her own org still resolves correctly, so the fix is not
merely hiding the leak behind a bug that breaks reads generally. Read
migration 0068 in full: this is not one shared helper — `app_resolve_node_setting`,
`resolve_shift_template`, and the `rename_week_template`/`delete_week_template`
pair each carry their own copy of the boundary clause, written by hand three
times to the same text (`(auth.uid() IS NULL OR ... = app_current_org())`).
That is a real risk on its own (the same text drifting apart is exactly how
0061 produced DEF-0019 in the first place), but not a defect against R-341 by
itself, since the text is currently identical everywhere it appears.

The pin (`src/test/defects/DEF-0018.test.ts`) is a migration-text reader, not
a live call; it has not been promoted out of `src/test/defects/`.
