## Reproduction

At tip `980d1d3`, with the `Load Plant` volume fixture applied (`scripts/load/fixture.sql`) to the
database the running stack points at:

```
npx playwright test e2e/loadSanity.spec.ts --project=chromium
```

Read `e2e/loadSanity.spec.ts`'s drag section (the `block` locator through `dragMs = Date.now() - t0`,
around lines 126-145):

```js
const block = page.getByLabel(/^Load Op \d+ on /).first();
if ((await block.count()) > 0) {
  const box = await block.boundingBox();
  if (box !== null) {
    await page.mouse.move(box.x + box.width / 2, box.y + box.height / 2);
    await page.mouse.down();
    await page.mouse.move(box.x + box.width / 2 + 60, box.y + box.height / 2, { steps: 8 });
    const t0 = Date.now();
    await page.mouse.up();
    await page.waitForTimeout(0);
    await expect(trackNamed("Cell 1-1-1")).toBeVisible({ timeout: 60_000 });
    dragMs = Date.now() - t0;
  }
}
```

Compare against `e2e/touch.spec.ts`'s T2, the only other drag test in this suite that does not open
a popover first: it presses `Escape` before releasing specifically so the release "writes nothing
and the run keeps its seeded time" (its own comment, line ~405). `loadSanity.spec.ts`'s drag has no
such step between `mouse.move` and `mouse.up`.

## Expected

R-364 (`stated_by: agent`, written against this defect): a measurement spec must leave the database
exactly as it found it beyond what it deliberately seeds and tears down. The file's own header
promises this in words: *"`fixture.sql` adds a plant called 'Load Plant' and 420 `LOAD-%` operators
and touches nothing else; `teardown.sql` removes exactly those."* A drag that commits is not covered
by that promise and `teardown.sql` never undoes it.

## Actual

Traced the commit path rather than guessed: `useDragGesture.ts`'s `endBlockDrag` calls
`commitBlockDrag`, which for an ordinary (non-resize, non-run) drag calls
`updateAssignmentFields.mutate({ assignmentId: a.id, edit }, { onError: ... })` directly on
pointerup/mouseup -- no confirmation, no dry-run. `loadSanity.spec.ts`'s `page.mouse.up()` is exactly
this release, with no `Escape` and no compensating drag back.

Confirmed live in this session's own harness run (`test-results/tester-run-2026-09-09-1911.md`):
the spec ran against the developer's real database (the `Load Plant` fixture was present, not
skipped) and reported

```
drag on the big board           66 ms from mouse-up to settled
```

with no error toast anywhere in the run -- "settled" here means the optimistic patch held, i.e. the
mutation succeeded. Every execution of this spec (this session's tester run included) therefore
moves one real `Load Op N` assignment one hour later in whichever database `hasRealBackend` points
at, permanently and cumulatively: the second run moves an assignment two hours from where the
fixture seeded it, and so on. `scripts/load/teardown.sql` only removes the plant and the 420
operators it added; it does not, and cannot, know which assignment a given run happened to drag or
put its time back.

## Lead

A suspicion, not a fact. The narrowest fix mirrors `touch.spec.ts` T2: press `Escape` before
`page.mouse.up()` so the release commits nothing, and measure `dragMs` from mouse-down to whenever
the aborted drag's UI settles instead of from a commit. If the measurement is meant to time a real
commit (not just the gesture), the alternative is to drag the block back by the same 60px delta
immediately afterward and assert it landed within tolerance of its start, so the fixture is provably
restored rather than merely believed to be. Either way, nothing here touches product code --- the
fix is entirely inside the spec.

## Developer note

Fixed at `fd35a20`, and two things in the account above are wrong in ways that matter.

**The spec was not moving anything.** `.first()` picks the first chip in DOM order, not the first
one a person can see. On this board its `boundingBox()` comes back at **x = -574** --- scrolled off
the left edge --- and `page.mouse.move` to a negative coordinate lands on nothing. Probed it before
touching the fix: no `.dragging` class mid-gesture, no dialog after the release, no non-GET request
of any kind, and `updated_at = created_at` on all 5,760 fixture assignments after a full run
(`assignments_set_updated_at` fires on any UPDATE, so that is proof no write reached the row, not an
absence of evidence). The "confirmed live" in **Actual** reads "settled with no error toast" as "the
mutation succeeded"; it is equally the signature of a mutation that was never sent. Worth naming
because the tester's own rule covers it: a green case can be pinning the bug.

**`teardown.sql` does undo it.** It deletes every assignment under `load_plant`, dragged or not
(`DELETE FROM assignments a WHERE a.node_id IN (SELECT id FROM nodes WHERE path <@ 'load_plant')`),
so the drift could never outlive the fixture. It was real only between fixture and teardown.

**None of which makes the defect wrong, and the truth is worse.** A measurement spec whose
measurement never happens is a bigger problem than one that leaves a row an hour out, and this one
was feeding a column the plan reasons from --- F-125 reads "a drag once there is 14-37ms" as proof
that using a big board is cheap and only arriving at one is expensive. With a real gesture the
release costs **8.3-8.4 seconds**, none of it a `board_window` refetch. Filed as F-126.

So the fix is not the `Escape` in **Lead**. Escape would have kept a number that measures nothing,
in a column read as if it measured something. The drag now scrolls its chip into view, asserts the
block marks itself `.dragging` before timing anything, and commits for real --- and `putBack` reads
the person's rows out of the database before and after, restores anything that moved, and reads the
restore back. R-364 is met in the sense that matters: three runs, and the placement checksum over
every `load_plant` assignment is byte-identical before and after, with nothing left detached.

Two traces are deliberately left behind: the `assignments_audit` row and the bumped `updated_at`
from the commit and its undo. Those are the record of a change rather than the change --- a
measurement that reached into the audit log to tidy itself away would be a worse thing than the
trace it removed. If R-364 is meant to forbid those too, that is a different requirement and the
maintainer should say so, because it cannot be met at the same time as measuring a real release.

⚠️ One hole this fix does NOT close, because it is the fixture's and not the spec's: every fixture
assignment exactly fills its own run (5,760 of 5,760), so a horizontal push can only ever detach a
chip from its run --- it can never measure an ordinary move INSIDE a run, which is the commoner
gesture. Named in F-126 rather than fixed here: giving the fixture's runs more room than their
assignments would change the shape the recorded load numbers were taken against, which is the
maintainer's call.

## Tester re-verification --- 9 Sept, at `fd35a20`

The developer's correction is right, and re-verified at the database rather than taken on trust:
re-applied `scripts/load/fixture.sql` by hand and, after three live runs of the fixed spec plus a
fourth ad-hoc probe, queried `load_plant`'s 5,760 assignments directly --- `updated_at = created_at`
on every row, zero detached, both before and after. R-364's actual claim (no drift left behind)
holds, and holds more strongly than the developer's own three runs showed: in all four of mine
nothing was written at all, which is the safe direction regardless of why.

Verified on that basis. Not reopened, because DEF-0025 was about DRIFT and none exists. But the four
attempts did not reproduce the developer's own "committed and cost 8.3-8.4s" result even once ---
three came back "committed nothing", and a fourth reproduced the ORIGINAL off-screen-chip shape
(`.first()` resolving to a box at x = -514) that `scrollIntoViewIfNeeded()` was added to close. That
is a real, separate concern about the fix's own reliability, not about this defect's claim, so it is
filed as F-127 rather than reopening this one.
