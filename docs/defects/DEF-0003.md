## Reproduction

Follow DEF-0002's five steps — the same click path produces both defects — and
read the toast that appears at the bottom of the board.

Or, with no browser, run the pin:

```
npx vitest run src/test/defects/DEF-0003.test.ts
```

## Expected

R-046: "Clients read the JSON error field; raw constraint violations are never
part of the contract." The server raised `not_offered_here` through `api_raise`
and `describeSchedulerError` already carries the right sentence for it —
`errors.ts:741` is a whole comment about naming the thing rather than the rule:
"what the person did was put a Plant 2 product on a Plant 1 cell, and the only
useful thing to say is which kind of row was in the wrong place and what to do
instead."

## Actual

The server sent a named, typed refusal:

```
HTTP 409  v1/rpc/create_run
{"code":"PT409",
 "details":"{\"id\": \"b30f1677-e8b4-4465-bf3d-58caf2c9c4b0\", \"kind\": \"product\", \"error\": \"not_offered_here\", \"node_id\": \"ce0d946d-d104-4c2e-be48-869220e3bad4\"}",
 "hint":null,
 "message":"That product does not belong to this part of the structure."}
```

The screen showed:

```
Something went wrong. Please try again.
```

which is `describeSchedulerError`'s `Unknown` branch — the message that asks
somebody to repeat an action that can never succeed.

The pin is red on this build, and its operator control passes:

```
FAIL  DEF-0003 > classifies the product refusal as NotOfferedHere
      AssertionError: expected 'Unknown' to be 'NotOfferedHere'
FAIL  DEF-0003 > says which kind of row was in the wrong place, not 'Something went wrong'
 ok   DEF-0003 > still classifies the operator refusal, which kept its owner_node_id
```

## Lead

A suspicion, not a fact — but the two shapes can be read side by side.

`parseDetail`'s `not_offered_here` branch (`src/lib/api/errors.ts:455-470`)
requires four keys before it will match:

```
hasStringProp(detail, "kind") && hasStringProp(detail, "id") &&
hasStringProp(detail, "owner_node_id") && hasStringProp(detail, "node_id")
```

Migration 0028 sent all four. Migration 0034 (D115, "a product belongs to a list
of plants") stopped sending `owner_node_id` for the two PRODUCT guards, because
a part now has many places and there is no single owner node to name:

```
20260901000034:161  jsonb_build_object('kind', 'product', 'id', new.product_id, 'node_id', new.node_id)
20260901000034:207  jsonb_build_object('kind', 'product', 'id', new.product_id, 'node_id', new.node_id)
20260903000040:178  jsonb_build_object('kind', 'product', 'id', new.product_id, 'node_id', new.node_id)
```

while the OPERATOR guard in the same file kept it:

```
20260901000034:187  jsonb_build_object('kind', 'operator', 'id', new.operator_id,
                                       'owner_node_id', v_owner, 'node_id', new.node_id)
```

So the parser is not broken — it is a week behind one of the two payloads it
reads, which is CLAUDE.md §4's "a column list that appears twice is a bug with a
delay on it" in its exact form. `tsc` cannot see it: the required keys are a
runtime string test, not a type.

Two things follow that are worth checking with the fix rather than after it:

- `CycleTimesPanel.tsx:428` is `if (err.kind === "NotOfferedHere")`. Migration
  0040's guard is the only thing that raises it for that panel and it omits
  `owner_node_id` too, so that branch appears to be **unreachable** — a written
  error message that cannot be shown.
- `ownerNodeId` is a field on the `NotOfferedHere` variant. If the product
  payload can no longer supply it, the variant needs it optional rather than the
  server needing to invent one; `describeSchedulerError`'s sentence does not
  appear to use it.
