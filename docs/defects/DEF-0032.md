## Reproduction

At tip `0e88783`, on the tester's own stack (or any stack with the edge runtime up):

```
npx playwright test e2e/signedIn.spec.ts --project=chromium
```

## Expected

R-369's own claim: *"In the admin rail, Activity comes before Settings."* The three vitest pins
that guard the rail's order were all updated for the swap in the same commit (5e17205):
`src/test/scaleAudit.test.ts` H2, `src/test/adminNoGrants.test.tsx` N7, and
`src/test/defects/DEF-0008.test.tsx` all now read `..., "Templates", "Activity", "Settings"`.
`e2e/signedIn.spec.ts:82`'s `"a company admin signs in and gets the whole admin rail"` test
asserts the same twelve-item rail from the browser and should read the same order.

`Received` (what the running app actually painted) is `..., "Templates", "Activity", "Settings"` --
the CORRECT, new order R-369 asked for. `Expected` (the test's own hardcoded array,
`e2e/signedIn.spec.ts:82-93`) still reads `..., "Templates", "Settings", "Activity"` -- the OLD
order, never touched by commit 5e17205. The product is right; this one copy of the list is wrong,
so a correct rail fails the browser suite while all three vitest copies of the same order pass.

Session 127's own `numbers_note` recorded the reason this was missed: *"`e2e` (44) carried, NOT
re-run"* -- the rail swap was proved by three vitest DOM pins but the browser suite was never run
against it before commit, so this fourth copy of the order was never exercised.

The other two rail-order-adjacent tests in the same file are unaffected: `"a site admin is offered
Settings and not Activity"` (line 108) uses `toContain`/`not.toContain`, not an ordered list, and
`"a supervisor with no admin grant gets exactly four tabs"` (line 122) asserts a four-item list
that contains neither Activity nor Settings.

## Lead

Not a suspicion -- read directly. `e2e/signedIn.spec.ts:87-88` should swap the two lines to match
the other three pins:

```diff
     "Templates",
-    "Settings",
     "Activity",
+    "Settings",
   ]);
```

This is the same "a column list that appears twice" shape CLAUDE.md already names for
`REM_SURFACES` -- here the rail's order lives in four places (three vitest pins plus this e2e
spec) and only three were updated in the same commit as the product change.

## Developer note

Fixed: `e2e/signedIn.spec.ts`'s company-admin rail array now reads
`..., "Templates", "Activity", "Settings"`, the same order as the three vitest pins and the running
app. This was the fourth copy of the rail order that R-369's swap should have touched; missed
because session 127 did not re-run the browser suite (`e2e` carried, not run). Verified by
inspection against the app's `SECTIONS`; the tester's cold `--e2e` run is the outside proof.

## Tester re-verification -- 10 Sept, at `c494cfe`

Re-ran cold on a freshly reset tester stack: `e2e\signedIn.spec.ts:80` (`"a company admin signs in
and gets the whole admin rail"`), the exact case this defect names, passed. Consistent across every
run this session once the edge runtime and the stack were both correctly up. Verified.
