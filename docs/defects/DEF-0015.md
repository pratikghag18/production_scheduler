## Expected

R-239: *"A client control is never hidden for something the server permits,
and never shown for something the server refuses."*

R-346, the viewer clause, in the maintainer's words: *"for a viewer, the left
panel serves no purpose, so we should hide it, **the only thing they see is
the board**."* And the server's own answer for this person, read off
`board_window` and the policies: `can_place: false`; `assignments_insert`,
`assignments_update` and `assignments_delete` are all `app_can_edit_node`,
which a viewer grant does not pass (`app_grant_paths(true)` is the
supervisor-or-admin set).

So a viewer should get no create form, no person picker, and no Save or
Delete — or, at the least, those controls disabled with the reason — not a
working form whose only outcome is a refusal.

## Lead

A suspicion, not a fact. `board_window` already sends the one boolean the
board needs (`can_place`), and `BoardPage.tsx` already reads it — for the
panel only (`{boardQuery.data.canPlace && (<OperatorPanel ... />)}`). The
create and assignment pop-ups are rendered from `popover?.kind` a few lines
below with no such guard, and the interaction hook opens them for anyone who
presses Enter on a track or clicks a chip. Two shapes would close it: do not
open the create pop-up and render the assignment pop-up read-only (no Person,
Save or Delete) when `canPlace` is false; or hand `canPlace` into both
pop-ups and let them disable their write controls with the reason. Either
keeps R-239 in both directions, since `can_place` is computed on the server
from the same `app_grant_paths(true)` set the write policies bind (0058).
`can_place` is per board root, not per cell; that is enough here because a
viewer grant never passes `app_can_edit_node` anywhere, but a supervisor
granted one line whose board is rooted higher would need the per-node
answer, which the board does not have today.

The pin reads `BoardPage.tsx`: the `<CreatePopover` and `<AssignmentPopover`
elements must each sit under a `canPlace` guard or receive a
`canPlace`/`readOnly`/`canEdit` prop, and it proves its own reader by finding
the panel's existing guard.

## Developer note

Agreed. The lead is the fix: `BoardPage` reads `can_place` once and hands it
down — to the panel (hidden), to `useDragGesture` (no create form on Enter or
click-drag, no block or panel drag, no arrow nudges), and to `AssignmentPopover`
and `RunPopover` as `readOnly` (the details and Close; no Person, no editable
field, no Save, no Delete). No pop-up decides for itself. Pinned by three
gesture-layer cases and six pop-up cases (`viewerBoard.test.tsx`), the pin is
green, and the demo world now has a viewer per plant (Viva, Vito, Vina; Vlad on
Plant D live), so `e2e/viewerBoard.spec.ts` signs in as Viva and reads it off
the screen: no panel, no Copy week, Enter on a track opens nothing, a chip
opens read-only. On the tester's caveat about `can_place` being per board root:
a supervisor's board is rooted at their grant, so the per-node answer is not
needed today; noted, not built.
