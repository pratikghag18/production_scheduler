## Reproduction

At the committed tip `3c8cdaf`, on the local stack (or the scratch SQL
database `run-sql-test.sh` builds). `rename_week_template` and
`delete_week_template` (migration 0067) are `SECURITY DEFINER`; their first
statement, `SELECT plant_id, org_id FROM week_templates WHERE id =
p_template_id`, bypasses `week_templates_select`'s RLS and can find a row in
ANY org. Fabricate one for org 2 (Contoso), then call both functions as Dana
(org 1's Plant A site admin) with a bogus id and with the real other-org id:

```
docker exec -i supabase_db_production_scheduler psql -U postgres -d postgres <<'SQL'
BEGIN;
insert into week_templates (id, org_id, plant_id, name, saved_from, created_by)
values ('99999999-0000-0000-0000-000000000001', '10000000-0000-0000-0000-000000000002',
        '3000000b-0000-0000-0000-000000000001', 'Contoso Template', '2026-09-07', null);

select set_config('request.jwt.claim.sub','00000000-0000-0000-0000-00000000dec1', true);
SET LOCAL ROLE authenticated;

DO $$ BEGIN
  PERFORM rename_week_template('88888888-0000-0000-0000-000000000000','x');
EXCEPTION WHEN OTHERS THEN RAISE NOTICE 'bogus id -> %', SQLERRM; END $$;

DO $$ BEGIN
  PERFORM rename_week_template('99999999-0000-0000-0000-000000000001','x');
EXCEPTION WHEN OTHERS THEN RAISE NOTICE 'org-2 id -> %', SQLERRM; END $$;

ROLLBACK;
SQL
```

The pin, which runs on every `npm run test`:

```
npx vitest run src/test/defects/DEF-0021.test.ts
```

## Expected

R-356 (`stated_by: maintainer`): *"A template is listed, renamed and deleted
by the plant's admins."* An admin who is not that plant's admin should be
refused the same way whether the template id is real (in a plant or company
she does not administer) or entirely made up -- the same standard
DEF-0016/17/18/19 name for every server-side resolver: a foreign row and a
bogus id give the same answer. `list_week_templates` already gets this right
(its own query carries `wt.org_id = app_current_org()`); rename and delete
should match it.

## Actual

```
NOTICE:  bogus id -> no such template
NOTICE:  org-2 id -> only this plant's admins may rename a template
```

The two refusals are different sentences with different `reason` codes
(`invalid_argument/no_such_template` versus `not_permitted/not_admin`), so a
caller who holds or guesses a template id can learn "this id belongs to a
real template, outside my company" from the shape of the refusal alone.
Repeated for `delete_week_template` with the same result; the row survives
either way (confirmed by count after the call, inside the same transaction,
before rollback) -- this is a pure information leak, not a write hole.

## Lead

A suspicion, not a fact. Both functions' existence check is `SELECT plant_id
[, org_id] FROM week_templates WHERE id = p_template_id` with no `org_id =
app_current_org()` term, unlike `list_week_templates`'s own query two
functions above them in the same file. Adding that term to the lookup (so a
row in another org is invisible to it, the same as a row that does not
exist) would make both branches converge on `invalid_argument /
no_such_template` for a foreign id, matching the bogus-id answer. The
org-scoped column is already selected in `rename_week_template` (`v_org` is
read and used for the duplicate-name check further down), so the fix may be
as small as adding the term to the initial `WHERE` clause and re-checking
that `v_plant IS NULL` after it.

## Tester re-verification — 8 Sept, at `0a8da7a`

Live, with a real foreign-company row rather than the transaction-scoped
fixture the original filing used: inserted one `week_templates` row directly
for org 2 (Contoso Fabrication, `10000000-...002`), committed (not rolled
back), then called both writers as Dana (org 1, Plant A site admin) over
PostgREST with her real bearer token.

```
rename_week_template(real org-2 id)  -> invalid_argument / no_such_template
delete_week_template(real org-2 id)  -> invalid_argument / no_such_template
row afterward: unchanged name, still present (not renamed, not deleted)
```

Same shape a bogus id gives, on both functions, and the row is provably
untouched (read back by id, name identical, still exists) rather than merely
"no error was raised" — the write-that-changes-nothing case this project has
been burned by before. The probe row was deleted afterward
(`DELETE FROM week_templates WHERE id = ...`).

This fix is independent code from DEF-0018/0019's node resolvers (a different
existence-lookup edit, `AND org_id = app_current_org()`, added to two PL/pgSQL
functions, no owner exemption since these are writer paths only reached by a
signed-in admin) — see DEF-0018's re-verification for why migration 0068 as a
whole is four hand-written copies of a boundary, not one shared mechanism.
The pin has not been promoted out of `src/test/defects/`.
