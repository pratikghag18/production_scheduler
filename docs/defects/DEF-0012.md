## Reproduction

At the committed tip `d5bfdf6`, in the running app and against the local stack.
The person this is about is one migration 0053 says cannot be made — the first
step makes one anyway, in a single request, over an ordinary site admin's own
session.

**1. Ask the RPC for it, as the screen does. It refuses, correctly.**

```
ANON=$(grep VITE_SUPABASE_ANON_KEY .env.local | cut -d= -f2-)
DANA=$(curl -s -X POST "http://localhost:54321/auth/v1/token?grant_type=password" \
  -H "apikey: $ANON" -H "Content-Type: application/json" \
  -d '{"email":"dana@example.test","password":"devpassword"}' | jq -r .access_token)

curl -s -X POST "http://localhost:54321/rest/v1/rpc/set_site_member" \
  -H "apikey: $ANON" -H "Authorization: Bearer $DANA" -H "Content-Type: application/json" \
  -d '{"p_node_id":"<Area 1>","p_profile_id":"<Ana>","p_role":"admin"}'
```

**2. Ask the table for it instead. It is given.**

```
curl -s -X POST "http://localhost:54321/rest/v1/profile_grants" \
  -H "apikey: $ANON" -H "Authorization: Bearer $DANA" -H "Content-Type: application/json" \
  -H "Prefer: return=representation" \
  -d '{"profile_id":"<Ana>","node_id":"<Area 1>","org_id":"<org>","role":"admin"}'
```

**3. Sign in as **Admin (company)**, go to **Admin → Access**, focus **Plant A**,
find `ana@example.test` and click the **Area 1** link under her name to focus
that node.** Read her row.

**4. Put it back:**

```
curl -s -X DELETE "http://localhost:54321/rest/v1/profile_grants?node_id=eq.<Area 1>&profile_id=eq.<Ana>" \
  -H "apikey: $ANON" -H "Authorization: Bearer $DANA"
```

**The pin makes the same statement about the function the screen obeys:**

```
npx vitest run src/test/defects/DEF-0012.test.ts
```

## Actual

**Two halves. The second is the one a person sees.**

### The rule lives in the RPC, not in the database

```
=== R1: Dana asks the RPC for admin on Area 1 ===
{"code":"PT400","details":"{\"error\": \"invalid_argument\", \"field\": \"role\",
 \"value\": \"admin\", \"reason\": \"admin_below_root\", \"node_id\": \"7971a218-…\"}",
 "message":"an admin runs a whole plant, so admin can only be given at a plant"}
HTTP 400

=== R2: Dana POSTs the same grant straight to the table ===
[{"profile_id":"a0000000-…-000000000002","node_id":"7971a218-…",
  "org_id":"10000000-…-000000000001","role":"admin"}]
HTTP 201

=== R3: read the row back ===
[{"profile_id":"a0000000-…-000000000002","node_id":"7971a218-…","role":"admin"}]

=== R4: and the server now treats her as an admin of Area 1 ===
 ana_company_admin | ana_admin_anywhere | ana_admins_area1
-------------------+--------------------+------------------
 f                 | t                  | t
```

Dana is a site admin, not a company admin — org-wide role `viewer`, one admin
grant on Plant A. `profile_grants`' RLS is `app_is_admin() OR
app_is_admin_for(node_id)`, and there is no CHECK constraint and no trigger on
the table, so `admin` below a root is refused by exactly one function and by
nothing else. An `UPDATE` works the same way: create the grant as `supervisor`
through the RPC, then `PATCH role=admin`, measured as `UPDATE 1` with the row
read back.

⭐ **The same schema does it right one table over.** Moving a plant root beneath
another node would turn a legal admin grant into an illegal one, and that path is
closed at the DATABASE, not at the RPC — `move_node` refuses, `place_node`
refuses through it, and a direct `UPDATE nodes SET parent_id = …` is refused by
the trigger `nodes_check_level_adjacency`:

```
ERROR:  node 1b3722c8-… level position is not exactly one below its parent's
DETAIL:  {"error": "level_mismatch", "node_id": "1b3722c8-…"}
```

So "the database says so first" is the standard this project already meets
elsewhere, and `profile_grants` does not meet it.

### And when such a row exists, the screen misreports it

Read off `http://localhost:5173/admin` as the **company admin**, Access focused
on Area 1 — the row's sentence and the row's control, side by side:

```
Who can get in — Area 1
Has access (2)
  admin@example.test   Company admin — reaches every plant   Nothing to take away here.
  ana@example.test     Admin of Area 1                       [ supervisor ▾ ]  [Remove]

select 0  aria=Role for ana@example.test  value="admin"  options=["supervisor","viewer"]
```

`value="admin"` is what React set; `options` is what `allowedRoles` returned. A
`<select>` whose value is not among its options renders the FIRST option, so the
screen says **supervisor** for a person it has just called **Admin of Area 1**.
Nothing is disabled and nothing explains it. An administrator who touches that
row and saves is saving `supervisor` — the value they were shown, not the one the
person holds — and to them it will look like they changed nothing.

**The pin, on this build:**

```
 FAIL  src/test/defects/DEF-0012.test.ts > … > someone else's below-root admin grant can still be shown as admin
AssertionError: the control would render options ["supervisor","viewer"] with value "admin", so the browser shows "supervisor": expected [ 'supervisor', 'viewer' ] to include 'admin'

 Test Files  1 failed (1)
      Tests  1 failed | 2 passed (3)
```

⛔ **R-340's own sentence is the thing that is false**, not a paraphrase of it.
It says the self-rule keeps `["admin"]` for such a row. `selfLocked` is
`row.isSelf && !viewerIsCompanyAdmin && row.directRole === "admin"` — it is about
the VIEWER'S OWN row and about a viewer who is not a company admin. Every other
row, which is every row an administrator actually works on, falls through to
`isPlantRoot ? GRANT_ROLES : ROLES_BELOW_ROOT`.

⚠️ **And the cases that were written for R-340 cannot see it.** A30 is the only
one aimed at this sentence and it passes `isSelf: true`; A48 is the "somebody
ELSE's admin grant" case and it passes `isPlantRoot: true`. There is no case for
somebody else's grant below a root, which is the exact combination. Verified by
mutation on a scratch copy: removing the narrowing entirely (`return
GRANT_ROLES`) is CAUGHT — A27 and A28 go red — so the group is not inert, it is
just missing this cell of the table.

⛔ **The server half of R-340 has no test at all, and that is measured.** Every
migration in this project has a numbered file in `supabase/tests/`; 0053 has
none, and `grep -rn admin_below_root supabase/tests/` returns nothing. Removing
the whole new block from 0053 on a scratch copy and rebuilding a database from it
leaves the SQL suite **identical**:

```
=== REAL BUILD (sql_test_db, unmutated) ===        total PASS=597  FAIL=1
=== MUTANT (admin_below_root rule removed) ===     total PASS=597  FAIL=1
```

(the one failure is DEF-0011's, in both runs). The client cases say of themselves
*"THESE CASES MIRROR A SERVER RULE AND ARE WORTH NOTHING ALONE"*, and the server
rule they mirror is checked by nothing.

## Lead

A suspicion, not a fact. Three separable pieces, and they are the developer's to
weigh:

**The screen.** `allowedRoles` already argues the case against itself, in its own
first paragraph: *"An empty list would leave the control with nothing selected
while the person is, in fact, an admin here; the honest rendering is a control
showing `admin` with no other option."* That reasoning does not depend on whose
row it is. The one-line shape that suggests itself is to widen the existing
clause from the self-rule to the fact it is really about — the person holds
`admin` HERE — rather than to who is looking:

```ts
if (row.directRole === "admin" && !isPlantRoot) return ["admin"] as const;
```

which leaves A27, A28, A29, A30, A31 and A48 as they are. Whether it should
instead render no control with a sentence naming the inconsistency is a product
call and is why this is a lead.

**The database.** A `CHECK` cannot see `nodes.parent_id`, so this is a trigger on
`profile_grants` in the shape `nodes_check_level_adjacency` already has, or a
policy the insert cannot satisfy. ⚠️ **It is worth putting to the maintainer
rather than assumed**, because R-238 carries a standing note saying direct
PostgREST writes past these RPCs are a known and accepted gap (`X46 asserts the
gap on purpose`). If that stays the position, then the honest repair is to soften
0053's header and the commit subject — "the database says so first" is not what
the migration does — and the screen half above still needs fixing on its own,
because a row 0053 says it deliberately leaves alone is enough to produce it with
no direct write at all.

**The missing SQL file.** `supabase/tests/77_admin_only_at_plant_root_test.sql`,
or whichever number is next, asking 0053's questions the way 48 and 49 ask 0021's
and 0022's: admin at a root stored, admin one level down refused with
`admin_below_root`, supervisor one level down still stored, and the row read back
each time. The developer measured exactly those three by hand and wrote the
results into DEF-0010's note; the work is turning that measurement into a file.

## Developer note

Agreed on all three parts, and the maintainer's standing position on direct
PostgREST writes did not need re-asking: R-238's note records the DELETE gap as
accepted, but this defect is about a write that CREATES a person the product
has decided not to have, which is a different thing from removing a row.

**The table.** 0054 adds `profile_grants_admin_at_root`, BEFORE INSERT OR
UPDATE OF role, node_id, raising `admin_below_root` in the shape
`nodes_check_level_adjacency` already has. Your two routes, replayed as Dana on
the live stack:

    POST profile_grants {role: admin, node: Area 1}  -> invalid_argument, admin_below_root
    supervisor via the RPC, then PATCH role=admin     -> refused (77's AR6, row read back)

Two things it had to learn, both measured and written into the migration
header. It binds exactly whom the table's policies bind and not the owner:
eleven cases in 46 and the fixtures of 47, 48, 51, 52, 53 and 56 build the
retired person as the owner so 0019's predicates stay right for rows that
predate the rule, and binding the owner left the suite at 527 / 12 / 205. And
it reads the node's shape through `app_node_is_plant_root`, a definer, rather
than through the caller's eyes, because failing closed on visibility made the
trigger refuse a cross-plant insert before the policy could (47's W28). AR5
shows a signed-in company admin IS bound, so the line is owner-versus-everyone.

**The screen.** `allowedRoles` no longer keys on whose row it is: somebody
else's below-root admin is drawn as `admin`, first, with `supervisor` and
`viewer` after it, the two moves the server will take. Re-selecting `admin` is
a no-op; the demotions are the repairs an administrator makes. A32 is the cell
A30 and A48 left out between them; A33 walks the property over every
combination. Your pin is green, 3 of 3, untouched.

**The file.** `77_admin_only_at_plant_root_test.sql`, nine cases, the row read
back each time. AR9 is the one worth reading: the owner can still make the row
0053 promised to leave alone, and the company admin can then demote it, so the
trigger refuses creating the state and not repairing it.

One case changed its contract on purpose: 47's W29 handed out `admin` on Line 1
by direct insert as a site admin; it hands out `supervisor` now and says why
in place. The rest of the suite is unchanged and whole: 607 / 0 / 0.
