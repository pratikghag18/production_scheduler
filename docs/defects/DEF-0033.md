## Reproduction

On EITHER stack, after any run of `e2e/invite.spec.ts`'s first two cases (`"an admin invites by
email..."` and `"a refused grant on a fresh invite leaves no orphan..."`):

```
docker exec <db-container> psql -U postgres -d postgres -c "select u.email, u.created_at from
auth.users u where u.email ~ 'invitee-|orphan-' order by u.created_at;"
```

or open the Access tab as `dana@example.test` on Plant A and read the "Has access" list -- every
row is a real, editable member with a role select, a place picker and a Remove button, exactly like
a real person.

## Expected

`e2e/invite.spec.ts`'s own header: *"Nothing a demo person relies on is touched."* The file's two
cases that complete a real invite --- `"an admin invites by email; the person sets a password and
lands with their grant"` (line 172) and `"a refused grant on a fresh invite leaves no orphan"`
(line 230, which deliberately finishes with a real viewer grant at the plant root to prove the
retry works) --- each mint a fresh `invitee-<Date.now()>@example.test` or
`orphan-<Date.now()>@example.test` address, invite it through the live Edge Function, and leave it
holding a real `profile_grants` row on Plant A. Nothing in the file removes either afterward, so
"nothing a demo person relies on is touched" holds for the NAMED demo people but not for the
tester's own database, which accumulates one new real account per run, forever.

Contrast `e2e/weekTemplates.spec.ts`, which at least TRIES: an `"E2E "`-prefixed name and an
`afterAll` cleanup call (buggy today, DEF-0030, but aimed at the right thing). `invite.spec.ts` has
no such attempt at all -- confirmed by reading the file for `afterEach`/`afterAll`/any delete call:
none exists.

## Lead

A suspicion on the fix, not on the mechanism (confirmed above by direct count). The two cases that
land a real grant could each remove it afterward the same way `runRemoveMember`/`remove_site_member`
already does for a normal user, or -- closer to their purpose, which is proving the INVITE path
works, not that the grant persists -- delete the auth user via the service-role client
(`supabase.auth.admin.deleteUser`) in a `finally`/`afterEach`, the same authority
`e2e/passwordReset.spec.ts` already holds for its own mail-catcher reads. A per-run prefix
(`invitee-`/`orphan-`) already exists and would let a maintenance script or a `beforeAll` sweep
remove anything older than a day, the same safety net `weekTemplates.spec.ts` leans on for its
"E2E " prefix.

## Developer note

Fixed (best-effort teardown): `e2e/invite.spec.ts` now records the two throwaway addresses that land
a real Plant A grant and, in `afterAll`, removes each grant AS DANA via `site_people` +
`remove_site_member` — the same authority a real admin uses. Every step is guarded so a cleanup that
cannot reach the stack never turns a passing test red.

One limit, stated plainly: this suite holds no service-role key, so it removes the GRANT but not the
`auth.users` row. Removing the grant takes the address out of the Access tab's member list, which is
R-370's claim; the orphaned account remains (grant-less, invisible in the member list, surfacing only
as a candidate on an exact-email search). A full delete would need `auth.admin.deleteUser` and a
service-role client the e2e env does not carry. Not verified by the developer (no local e2e run); the
tester's cold `--e2e`, then a second run reading the member count, is the proof.

## Tester re-verification -- 10 Sept, at `c494cfe`

Re-ran cold on a freshly reset tester stack. Read `profile_grants` directly (a join, not the
suite's own colour) for the two addresses this run's `invite.spec.ts` cases minted: both hold zero
grants afterward (`role`/`node_id` both null through the left join), confirming they will not
render in the Access tab's "Has access" list. The fix's own stated limit holds too: both `auth.users`
rows remain (2 accounts matching `invitee-|orphan-`), exactly as documented, and exactly R-370's
own scope -- the member list, not the account. Verified.
