## Lead

**A suspicion, not a fact.** `resolve.ts`'s clear of everyone builds per-block commands (~3763: a
block crossing one edge of the day becomes an end-edge move to midnight) and then, per run
overlapping the day, a `remove_run` (~3812-3871) that `delete_run` executes in `cascade` mode --
which deletes every assignment with that `run_id` regardless of time (the reviewer's comment at
~3819 says so, and handles the crew blocks outside the window by listing them, but not the blocks
the same lot trims). So a run that crosses the day's edge takes the trimmed block and its own
out-of-day part with it. The lot reported a state that was not
the state written. The typed walk (DEF-0042) runs this exact sentence first and would have shown
it on the current seed. A question for the maintainer rides on the fix: when Monday is cleared,
does Sunday's night crew keep Sunday 22:00-24:00, or does a night shift belong wholly to the day it
starts?

## The maintainer's decision -- 28 Sept (now R-461)

The question this defect carried is answered: "The night shift, each day is its own bucket, what we
can do though is when we clear Monday for example, the board can ask the user if they want to clear
the portion of the shift for the previous day." So a clear of Monday removes Monday's part of every
block AND of every job on the place, keeps Sunday's part, and asks first whether Sunday's part of that
shift should go too. The expected behaviour of this defect is R-461's claim; the pin's invariant (no
part the lot says it keeps is removed by another step of the same lot) holds under it unchanged.

Amended the same day: the maintainer wants the question for the other direction too -- "we should
ask a question in this case as well and let the user choose to answer yes or no." Clearing Monday,
a shift that starts Monday 22:00 and runs to Tuesday 06:00 asks, yes or no, whether Tuesday's part
goes as well. R-461 carries both.

## Developer note

28 Sept, session 194. Fixed under R-461 as the maintainer decided it; the pin stays red and cannot be
made green by any resolver, so the reproduction is what to re-run.

The pin calls the clear with no answer and then asserts three things of the one result: that a trim
of `priyaBlk` is in the lot (l.126), that a removal of `run1` is in the lot (l.127), and that the two
are not both in the lot (l.133). The first two are the defect's own shape; the third is its absence.
Under R-461 the clear of a day that a night shift crosses answers with a question first, so
`res.ok` is false at l.111 and the case stops there. With an answer given, the lot holds either the
trims (No: Priya's block and the job both end at midnight, nothing removed whole) or the removals
(Yes: the block and the job both go whole), never one of each.

What holds the invariant now: `commandResolve.test.ts` ND1 to ND14 and NW1 to NW5 (no assignment the
lot keeps or trims sits under a removal; no job removed whole has a crew block the lot says stays),
