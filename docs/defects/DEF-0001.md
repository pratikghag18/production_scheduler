## Reproduction

Run the smoke test against a clean dummy-backend server — the exact state
`ci.yml` uses (`VITE_SUPABASE_URL=https://example.supabase.co`), so no session
and no data:

```
# terminal 1 — a throwaway dev server with dummy Supabase values, on a spare port
VITE_SUPABASE_URL=https://example.supabase.co VITE_SUPABASE_ANON_KEY=dummy-anon-key \
  npx vite --port 5174 --strictPort

# terminal 2 — the repo's own e2e, pointed at that server
npx playwright test --config <a config whose baseURL is http://localhost:5174 and
                               whose webServer block is removed>
```

Equivalently, and more simply: this is exactly what `npm run e2e` does inside
`.github/workflows/ci.yml` (job `build-and-test`, step `npm run e2e`). That
workflow triggered on `[main]` for the repository's first 43 commits while the
default branch was `Development`, so it never ran; commit `21c868f` widened the
trigger to `branches: [main, Development]` plus `pull_request`, so the next push
is the first time CI has ever executed this step.

## Expected

R-321 (filed as R-304, renumbered on merge): "a signed-out visitor to any route other than `/sign-in` is redirected to
`/sign-in` ... The committed e2e smoke test (`e2e/smoke.spec.ts`) must therefore
pin the app as it is — the sign-in redirect — and `npm run e2e` must be green on
`main`." The app already behaves this way: `src/routes.tsx` wraps the whole shell
in `<RequireAuth />`, which redirects a sessionless visitor to `/sign-in`
(`src/features/auth/RequireAuth.tsx:39-45`). The product is correct; the test is
what is stale.

## Actual

All three smoke cases fail. Against the clean dummy-backend server on 5174 the
signed-out visitor is served the sign-in screen, not the Board:

```
  1) [chromium] › e2e\smoke.spec.ts:35:1 › D97: a visitor with no session is offered no Admin link
    Error: expect(locator).toBeVisible() failed
    Locator: getByRole('heading', { name: 'Board', level: 1 })
    Expected: visible
    Timeout: 5000ms
    Error: element(s) not found

  3 failed
    [chromium] › e2e\smoke.spec.ts:28:1 › the shell and the board render without a backend
    [chromium] › e2e\smoke.spec.ts:35:1 › D97: a visitor with no session is offered no Admin link
    [chromium] › e2e\smoke.spec.ts:48:1 › D97: /admin visited directly refuses instead of rendering
```

The page snapshot Playwright captured at the moment of failure is the sign-in
screen, not the signed-out shell:

```yaml
- heading "Production Scheduler" [level=1]
- paragraph: Sign in to continue.
- text: Email
- textbox "Email"
- text: Password
- textbox "Password"
- button "Sign in"
- text: "Dev sign-in (local only): Viewing as:"
- combobox "Viewing as:":
  - option "Signed out" [selected]
```

Case 3 (`/admin` while signed out) fails the same way: it waits for a "Not
available" heading, but the sign-in gate intercepts the visit before
`RequireAdmin` is ever reached, so the D97 refusal screen the test asserts is
never rendered for a signed-out actor.

## Lead

The app is right; the test is a week behind it. `e2e/smoke.spec.ts` was
deliberately rewritten in `f2ac33d` around a *signed-out Board shell* — its
header even reasons that "`useSession` calls `loadProfile(null)` ... so
`adminAccess` settles on 'denied'" and the Board renders. P1-6b (session 19,
Sep 1) then wrapped the whole shell in `RequireAuth` and removed that shell:
there is no signed-out Board any more, only a redirect to `/sign-in`. The test
warns about exactly this failure mode in its own comment ("A test that has never
executed is not a test — it is a file") and has now reproduced it a second time.

The developer's call, but the shape of a fix: rewrite the three cases to pin the
app as P1-6b left it — `/` while signed out shows `heading "Production
Scheduler"` and `paragraph "Sign in to continue"` and no Admin link; `/admin`
while signed out lands on `/sign-in`, not "Not available". Note that once the
signed-out cases assert the sign-in redirect, D97's genuine admin refusal
("Not available" for a signed-in non-admin) is left with no e2e that reaches it —
R-D97 is still `verified_by: []`. This is a stale-test / broken-CI defect, not a
product bug; no vitest pin is written because the reproduction is a browser run,
given as the command above.
