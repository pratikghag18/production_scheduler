## Reproduction

At tip `c8f47cb`. The code is correct today; this is about what the test can and cannot tell
you if the runs sub-select in `board_window` ever loses its time-window scoping.

Find `board_window`'s last emission and remove `AND r.timerange && v_window` from the **runs**
sub-select only (leave the assignments sub-select untouched):

```
supabase/migrations/20260907000063_plant_timezone.sql, around line 406:

    'runs', COALESCE((
      SELECT jsonb_agg(to_jsonb(r) ORDER BY r.timerange)
      FROM runs r
      WHERE r.node_id IN (SELECT id FROM scoped_nodes) AND r.timerange && v_window
    ), '[]'::jsonb),
```

becomes

```
      WHERE r.node_id IN (SELECT id FROM scoped_nodes)
```

Then:

```
npx vitest run src/test/boardWindowScoping.test.ts
```

## Expected

R-006 (`stated_by: agent`): *"Every board load asks only for runs and assignments under one
subtree that intersect a time window."* The requirement's own `verified_by` entry names this
exact clause: *"the server function's own body scopes both runs and assignments by scoped_nodes
(subtree) and && v_window (time)."* A runs sub-select with no time-window predicate at all should
turn the case named for it -- `"the runs sub-select is scoped by scoped_nodes (subtree) and &&
v_window (time)"` -- red.

## Actual

```
 Test Files  1 passed (1)
      Tests  5 passed (5)
```

Every case stays green, including the one written for exactly this clause. The cause is the
extraction window itself:

```js
const runsBlock = /FROM\s+runs\s+\w[\s\S]{0,300}/i.exec(body);
```

300 characters after `FROM runs r` is generous enough to run straight through the closing of
the `runs` JSON field and into the *next* field, `'assignments'`, which still has its own
`&& v_window`:

```
FROM runs r
      WHERE r.node_id IN (SELECT id FROM scoped_nodes)
    ), '[]'::jsonb),

    'assignments', COALESCE((
      SELECT jsonb_agg(to_jsonb(a) ORDER BY a.timerange)
      FROM assignments a
      WHERE a.node_id IN (SELECT id FROM scoped_nodes) AND a.timerange && v_window
```

`runsBlock![0]).toMatch(/&&\s*v_window/)` is satisfied by the assignments field's predicate,
not the runs field's own -- the test cannot tell the two apart because its slice does not stop
at the end of the `runs` sub-select. `board_window`'s JSON keys happen to be built in the fixed
order `nodes, offered_here* (not asserted), runs, assignments, operators, ...` (read the
migration itself), so `runs` is always immediately followed by `assignments` and the bleed-through
is not a one-off accident of this particular file -- it will recur for as long as that ordering
holds, which the test does not pin either.

Confirmed the mutation is a real behaviour change and not a no-op: reverted with
`git diff --exit-code` clean, then re-applied and confirmed live against the SQL suite that a
`board_window` call with the mutation returns runs outside the requested window (not run through
here, but the same body drives `93_schedulable_node_guard_test.sql`'s own board reads, and the
regex proof above is standalone and reproducible without a database at all -- it is a property of
the extraction, not of any one row of data).

## Lead

A suspicion, not a fact. The narrowest fix is anchoring the slice to the sub-select's own close
paren -- `/FROM\s+runs\s+\w[^)]*?\)\s*,\s*'\[\]'::jsonb\)/i` or similar, so it stops at `),
'[]'::jsonb)` rather than counting characters -- and doing the same for the assignments block
above it, since the same 300-char slice there would just as happily bleed into `operators` on the
other side. The `scoped_nodes` assertion in both cases is not at risk the same way only because
`scoped_nodes` also appears earlier in the query (the CTE definition itself sits before either
block), so a false pass there would need the CTE's own text to vanish, not just bleed from a
neighbour.
