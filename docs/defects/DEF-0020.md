## Expected

R-351 (`stated_by: maintainer`): *"An email already in this org answers
already_member; one in another org is refused and nothing is said about the
other org."* Dana asking about `sofia@contoso.example` (a real person, in
org 2) should get the same shape she would get for a genuinely unknown
address's `not_admin`/`other_org` refusal family -- specifically
`{ ok: false, reason: "other_org" }` -- and no auth-user creation attempt.

## Actual

```
{"ok":false,"reason":"invalid","error":{"code":"PT400","message":"invalid argument","details":"{\"error\":\"invalid_argument\",\"field\":\"email\",\"reason\":\"Database error saving new user\"}"}}
```

`reason` is `"invalid"`, not `"other_org"`, and the message names a database
save failure -- which only happens when `auth.users.email` already exists.
Checked afterward: no orphan was left (GoTrue's own insert failed before this
function wrote anything), but the RESPONSE SHAPE itself is the leak: it is
distinguishable from both a genuinely free email (`ok:true, invited:true`)
and the intended other-org answer (`ok:false, reason:"other_org"`), so an
admin -- or anyone who can reach this function with any admin grant at all,
anywhere in their own org -- can learn "this email exists somewhere in this
Supabase project, outside my own org" for any address they choose to probe,
by the shape of the failure alone. Inviting `ana@example.test` (a real,
properly-credentialed org-1 address) from Dana correctly answers
`{"ok":true,"userId":"...","invited":false}` (the `here`/`already_member`
branch), confirming the bug is specific to auth rows GoTrue's own admin API
cannot list, not to every existing address.

## Lead

A suspicion, not a fact. `findAuthUser` (`supabase/functions/invite/index.ts`)
locates an existing account by paging `admin.auth.admin.listUsers` and
matching on email client-side. GoTrue's `listUsers` appears to filter (or
simply never index) rows whose `instance_id` is not the local instance's
zero-uuid, which is exactly the shape every row this project creates by raw
SQL fixture (rather than through `signUp`/`inviteUserByEmail`) has, unless a
migration explicitly upgrades it the way `dev_demo.sql` §7 does for nine
named accounts. `findAuthUser` returning `null` for an address that in fact
exists is indistinguishable, inside the function, from the address being
genuinely free, so the brand-new branch runs and `admin.auth.admin.inviteUserByEmail`
is the first thing to notice, via Postgres's own uniqueness constraint on
`auth.users.email`, surfacing as an opaque `invErr.message` the function
currently passes straight through as `invalidArgument("email", invErr?.message)`.

Two ways to close it, for the developer to weigh: (1) `findAuthUser` reads
`auth.users` directly with the service-role client (`admin.from("auth.users")...`
is not exposed via PostgREST, but a `SECURITY DEFINER` RPC scoped to exactly
"does an auth user exist for this email" would see every row regardless of
`instance_id`); or (2) treat `invErr` from `inviteUserByEmail` whose message
matches a duplicate/uniqueness shape as the SAME branch as "known auth user,
no profile", not as `invalid_argument` -- re-deriving `existing` from the
failure rather than trusting `findAuthUser`'s emptiness. Either way, the
`other_org` promise should not depend on every row in `auth.users` having
been created through GoTrue's own write path. Practical severity is minor:
no path this app's own product code takes creates an `auth.users` row with a
NULL `instance_id` (only `seed.sql`'s fixture block does, for org 2's two
people, deliberately never credentialed since nobody is meant to sign in as
them), so this does not appear reachable against a real tenant's own data
today -- filed because the invariant itself measurably breaks, and because a
future bulk-import or migration that touches `auth.users` directly would
walk into it silently.

## Tester re-verification — 8 Sept, at `0a8da7a`

Ran the pin (`npx vitest run src/test/defects/DEF-0020.test.ts`) both alone
and inside the full suite. Alone, and inside a fresh `npx vitest run` of the
whole suite (2495/2495), it is green. In the ONE full run made through
`scripts/tester-run.mjs --sql --e2e` (which also rebuilds the SQL scratch
database and runs Playwright in parallel beforehand), it failed on a plain
5000ms test timeout, not a wrong answer — the edge function took longer than
the pin's default timeout to answer under that load. Re-run alone immediately
after, it passed in 602ms. Recorded as environment flakiness under heavy
concurrent load, not a reopened defect: the pin's assertion never received
and rejected a wrong value, it never received a value in time. Worth the
developer's attention as a hardening item (the pin has no explicit timeout
override) but not evidence the fix regressed.

This fix is NOT part of migration 0068's node-resolver boundary; it lives
entirely in `supabase/functions/invite/index.ts`'s `isAlreadyTaken`, a
message/code string match on GoTrue's observed failure shapes
(`email_exists` / `user_already_exists` / the literal substring "database
error saving new user"). That is a materially different, more fragile
mechanism than the SQL predicate DEF-0018/0019/0021 share the shape of: it
depends on GoTrue continuing to phrase this specific failure the same way in
a future version. Filed nowhere new because the developer's own header
already says as much and it is the documented, deliberately-narrower "second
closure" the review brief asked for, not an oversight.

The pin has not been promoted out of `src/test/defects/`.
