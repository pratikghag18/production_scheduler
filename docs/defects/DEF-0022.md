## Reproduction

At tip `0a8da7a`. The code is correct today; this is about what the suite can
and cannot tell you when it stops being correct.

Mutate the one line that sets a part-day absence's stored range:

```
sed -i "s/tstzrange(p_starts_at, p_ends_at, '\[)')/tstzrange(p_starts_at, p_ends_at, '[]')/" \
  supabase/migrations/20260907000069_absence_by_the_hour.sql
```

Rebuild the scratch database and run the absences suite:

```
bash scripts/run-sql-test.sh --rebuild
bash scripts/run-sql-test.sh 88_absences_test.sql
```

## Expected

R-359 (`stated_by: maintainer`): *"a person out 09:00-13:00 is a clash for
the morning shift and not the night one"* -- the boundary is the whole point
of the requirement, and it is a half-open range (`'[)'`) on purpose (0069's
own header: "mirrors Postgres's `&&` on two `[)` ranges exactly"). A mutation
that closes the upper bound, so a shift starting the instant the absence ends
is wrongly caught, should turn at least one named SQL case red.

## Actual

```
---- 88_absences_test.sql : 27 passed, 0 failed, 0 hard-errors ----
```

Every case, including AB15 ("absence_overlap by the HOURS --- part-day
09:00-13:00 clashes with an overlapping shift and not with one outside those
hours"), stays green. Reading AB15 itself
(`supabase/tests/88_absences_test.sql`): its "miss" case is a shift at
14:00-16:00, a full hour clear of the absence's 13:00 end -- nowhere near the
boundary the mutation moves. No other case in the file asks about a shift
touching the exact instant a part-day absence starts or ends.

Confirmed the mutation is a real, live behaviour change and not a no-op:
direct calls against the mutated database --

```
set_absence(operator, '2027-06-11','2027-06-11','dentist',NULL,'09:00Z','13:00Z')
absence_overlap(operator, tstzrange('13:00Z','15:00Z'))  -- shift starting exactly when the absence ends
-> {"absent": true}     (mutated: wrong)
-> {"absent": false}    (unmutated, reverted: right)
```

The client's own mirror (`src/lib/absence.ts`'s `absenceGaps`) IS pinned on
this exact case -- `src/test/absence.test.ts`, *"a shift ending exactly when
the absence ends does not clash (half-open, touching is not overlapping)"* --
and R-359's own `verified_by` entry for that file claims the SQL suite proves
the same thing "by the same names the SQL cases carry." It does not; only the
client side does.

The developer's own pin, `src/test/defects/DEF-0022.test.ts`, proves the
LIVE server function gets the boundary right today (a real call over
PostgREST as Dana, not a read of migration text) -- this defect is that the
SQL suite cannot tell you if that ever changes, not that it is currently
wrong.

## Lead

A suspicion, not a fact. `88_absences_test.sql`'s AB15 was written to prove
"hours, not days" against a coarse counter-example (a shift on the same day
but hours away), which is the right case for proving the branch exists at
all, but is a different case from proving WHERE the boundary sits. The
smallest fix is one more named case beside AB15 -- a shift starting exactly
at the absence's `ends_at` (must not clash) and one ending exactly at its
`starts_at` (must not clash), mirroring `absence.test.ts`'s two boundary
`it`s by name -- rather than widening AB15 itself, since AB15's own miss case
is still worth keeping as the "clearly outside" sanity check.
