## Reproduction

At tip `0a8da7a`. The code is correct today; this is about what the suite can
and cannot tell you when it stops being correct.

Mutate the one line that sets a part-day absence's stored range:

```
sed -i "s/tstzrange(p_starts_at, p_ends_at, '\[)')/tstzrange(p_starts_at, p_ends_at, '[]')/" \
  supabase/migrations/20260907000069_absence_by_the_hour.sql
```

Rebuild the scratch database and run the absences suite:

```
bash scripts/run-sql-test.sh --rebuild
bash scripts/run-sql-test.sh 88_absences_test.sql
```

## Expected

R-359 (`stated_by: maintainer`): *"a person out 09:00-13:00 is a clash for
the morning shift and not the night one"* -- the boundary is the whole point
of the requirement, and it is a half-open range (`'[)'`) on purpose (0069's
own header: "mirrors Postgres's `&&` on two `[)` ranges exactly"). A mutation
that closes the upper bound, so a shift starting the instant the absence ends
is wrongly caught, should turn at least one named SQL case red.

## Actual

```
---- 88_absences_test.sql : 27 passed, 0 failed, 0 hard-errors ----
```

Every case, including AB15 ("absence_overlap by the HOURS --- part-day
09:00-13:00 clashes with an overlapping shift and not with one outside those
hours"), stays green. Reading AB15 itself
(`supabase/tests/88_absences_test.sql`): its "miss" case is a shift at
14:00-16:00, a full hour clear of the absence's 13:00 end -- nowhere near the
boundary the mutation moves. No other case in the file asks about a shift
touching the exact instant a part-day absence starts or ends.

Confirmed the mutation is a real, live behaviour change and not a no-op:
direct calls against the mutated database --

```
set_absence(operator, '2027-06-11','2027-06-11','dentist',NULL,'09:00Z','13:00Z')
absence_overlap(operator, tstzrange('13:00Z','15:00Z'))  -- shift starting exactly when the absence ends
-> {"absent": true}     (mutated: wrong)
-> {"absent": false}    (unmutated, reverted: right)
```

The client's own mirror (`src/lib/absence.ts`'s `absenceGaps`) IS pinned on
this exact case -- `src/test/absence.test.ts`, *"a shift ending exactly when
the absence ends does not clash (half-open, touching is not overlapping)"* --
and R-359's own `verified_by` entry for that file claims the SQL suite proves
the same thing "by the same names the SQL cases carry." It does not; only the
client side does.

The developer's own pin, `src/test/defects/DEF-0022.test.ts`, proves the
LIVE server function gets the boundary right today (a real call over
PostgREST as Dana, not a read of migration text) -- this defect is that the
SQL suite cannot tell you if that ever changes, not that it is currently
wrong.

## Lead

A suspicion, not a fact. `88_absences_test.sql`'s AB15 was written to prove
"hours, not days" against a coarse counter-example (a shift on the same day
but hours away), which is the right case for proving the branch exists at
all, but is a different case from proving WHERE the boundary sits. The
smallest fix is one more named case beside AB15 -- a shift starting exactly
at the absence's `ends_at` (must not clash) and one ending exactly at its
`starts_at` (must not clash), mirroring `absence.test.ts`'s two boundary
`it`s by name -- rather than widening AB15 itself, since AB15's own miss case
is still worth keeping as the "clearly outside" sanity check.

## Tester re-verification — 8 Sept, at `6b0f750`

Re-ran the exact original reproduction cold: mutated
`supabase/migrations/20260907000069_absence_by_the_hour.sql`'s
`tstzrange(p_starts_at, p_ends_at, '[)')` to `'[]'`,
`bash scripts/run-sql-test.sh --rebuild`, `bash scripts/run-sql-test.sh
88_absences_test.sql`. Where every one of 27 cases used to stay green, AB23
now goes red by name (`FAIL AB23: a shift starting exactly when the absence
ends was wrongly flagged`), and the same mutation also turns AB25 red
(`unexpected this person already has an absence over some of those days`) --
closing the upper bound makes the exclusion constraint's own touching pair
genuinely overlap too. AB24 stays green, correctly, since this mutation does
not touch the lower bound.

Went past the one reported mutation, as the reproduction alone only proves
this exact case is caught, not that the fix is general. Reverted, then tried
three more, each rebuilt and reverted before the next:
`git diff --exit-code` on the migration confirmed clean between each.

1. The mirror, `'[)'` to `'(]'` (open the low end instead of the high one):
   AB23 goes red again (now for the opposite reason -- the absence's END
   becomes inclusive too), AB25 stays green, and **AB24 does NOT go red**.
   Checked this is not a bug in my mutation: mathematically, AB24's window
   (`tstzrange('07:00','09:00')`, default `'[)'`) already EXCLUDES 09:00 by
   its own upper bound regardless of what the stored absence's lower bound
   is, so no boundary-type mutation of the absence's own range can ever make
   this specific case answer wrongly -- the window's own convention protects
   it. AB24 is not a case that can fail on this axis; it happens to always
   pass. This is worth the developer knowing, though it is not itself a
   defect: the only way "a shift ending exactly when a part-day absence
   starts" could ever wrongly clash is a bug in how the CALLER constructs the
   window, not in `set_absence`'s own range, and that is a different pin's
   job.
2. An off-by-one on the value itself (`p_ends_at + interval '1 hour'`,
   distinct from a boundary-type change): AB23 goes red by name again
   (the shift starting at the true 13:00 now falls inside the wrongly
   widened 09:00-14:00 stored absence), and AB25 goes red too (the two
   touching absences in that case now genuinely overlap under the same
   widening). AB24 stays green, correctly, since this mutation is entirely on
   `p_ends_at`.
3. Fully open, `'[)'` to `'()'`: every one of the 30 cases in
   `88_absences_test.sql` stays green -- this mutation is NOT caught by
   anything named. Checked live before concluding anything (the same
   discipline as the original filing): a direct `absence_overlap` call for a
   shift starting exactly at the absence's own start (09:00-10:00 against a
   09:00-13:00 absence) still answers `absent: true` under the mutation,
   because that window has an hour of real duration and overlaps the
   absence's interior regardless of whether the absence's own start is
   inclusive or exclusive -- a genuine boundary-sensitive test at that exact
   point is not constructible with any non-empty window, and Postgres treats
   a zero-width range as empty (handled by an early `absent: false` return
   before the comparison in question is ever reached). So this fourth
   mutation being uncaught is not itself a coverage gap the way the original
   filing was: nothing behaves differently in a way any placement could
   observe. Filed separately (DEF-0023) is a related but distinct finding --
   R-359's own corrected claim still names this exact scenario ("a shift
   starting exactly when the absence starts, which does clash") as "mirrored
   in 88_absences_test.sql by the name it carries there," and no such case
   exists there by any name.

`npx vitest run src/test/defects/DEF-0022.test.ts src/test/absence.test.ts` --
`Test Files 2 passed (2)`, `Tests 19 passed (19)`, against the live server,
unaffected by any of the above (all scratch-database mutations). Migration
0069 confirmed byte-identical to HEAD after the last revert
(`git diff --exit-code`). Verified: two of the three named boundary cases
(AB23, AB24) are now real and independently provable by mutation; the third
scenario named in R-359's own claim was never real and still is not, which
is DEF-0023, not a reopening of this one. The pin has not been promoted out
of `src/test/defects/`.
