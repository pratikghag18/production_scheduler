## Reproduction

```
grep -n "OperatorPanel.module.css\|ShiftLayer.module.css" src/test/scaleAudit.ts   # no hits
```

`src/test/scaleAudit.ts` is the enforcement half of R-D84. It names its surfaces in two hand-kept
lists — `CHROME_FILES` (board chrome that must scale with `--ui-scale`) and `REM_SURFACES` (admin
stylesheets that must size in rem). The completeness guard that stops a new surface from silently
escaping — the `missingRemSurfaces` walk, added as D89 after `ShapePicker.module.css` "sat outside
the D84 audit while the audit reported green" — states in its own comment that it *"walks the **admin**
feature directory."* There is no equivalent walk of `src/features/board`.

So a new board stylesheet is audited only if a person remembered to add it to `CHROME_FILES`, and
nothing fails if they did not. Two board panels added this window are in neither list:

```
src/features/board/components/OperatorPanel.module.css   (operator rail, S65)
src/features/board/components/ShiftLayer.module.css       (shift band on cells, S66-c)
```

## Expected

R-D84's claim: *":root font-size is 100% times --chrome-scale ... and new surfaces size in rem.
Breakpoints stay in px. The board keeps calc(px * scale) because its geometry is computed ..."* The
audit that proves R-D84 (`scaleAudit.test.ts`) must cover **new surfaces**, board ones included —
that is the whole point of the D89 completeness guard: adding a surface without auditing it should be
a test failure, not something noticed on a 4K monitor three briefs later.

## Actual

The suite is green (`scaleAudit.test.ts` passes) while the operator rail and the shift band are
audited by nothing. The rail's stylesheet in fact mixes the scaling idiom with bare pixels —

```
src/features/board/components/OperatorPanel.module.css
  10:  width: calc(190px * var(--ui-scale, 1));     <- scales
  82:  width: 8px;                                    <- does not
  91:  gap: 6px;                                      <- does not
  92:  padding: calc(10px * var(--ui-scale, 1)) ...   <- scales
```

so whether it honours R-D84's "the board keeps calc(px * scale)" is exactly the question the audit
exists to answer, and the audit is not asked. This is not a proven visual defect — some bare pixels
(a 1px hairline, an 8px grab handle) are legitimate under the standard — it is a coverage hole: the
guard cannot fail for a file it never reads.

## Lead

**A lead, not a fact — the developer decides.** Give the board the same completeness guard the admin
tree has: extend the `missingRemSurfaces`-style walk (D89) to `src/features/board`, deciding for each
board `*.module.css` whether it belongs in `CHROME_FILES` (scales via `--ui-scale`) or an explicit
board-pixel ignore list, and fail when one is in neither — the same two-place edit the admin side
already forces. Then enrol `OperatorPanel.module.css` and `ShiftLayer.module.css` and let the audit
judge their bare pixels. The pin (`src/test/defects/DEF-0036.test.ts`) asserts `scaleAudit.ts` names
both files; it goes green once they are brought under the audit by whichever list.
