## Reproduction

In the running app (a dev server on the committed tip `a4e938a`):

1. Sign in with the dev switcher as **Dana (site admin, Plant A)**.
2. Go to **Admin** and read the rail down the left.

Then, to see what the server would have allowed her, over her own session:

```
POST /rest/v1/rpc/set_node_setting
  { "p_node_id": "<Plant A>", "p_key": "eligibility_policy", "p_value": "__probe__" }
```

An illegal value on purpose: `set_node_setting` checks PERMISSION before it
looks at the value, so the refusal that comes back says which gate stopped her,
and nothing is written either way.

## Expected

R-239: "A client control is never hidden for something the server permits, and
never shown for something the server refuses."

R-333's claim, on the tab itself: "choose a plant and the tab edits THAT plant's
values."

And `SettingsPanel.tsx`'s own header, which was written for exactly this person:

> ⚠️⚠️ A SITE ADMIN REACHES THIS PANE — `adminSectionsFor` returns "all" for
> anyone with `adminAnywhere === true`, and a site admin holds an admin GRANT.
> On the company scope they see both controls DISABLED with the reason in words
> ... on **THEIR OWN plant they get working pickers**, because
> `set_node_setting`'s gate is `app_is_admin() or app_is_admin_for(node)`. On a
> plant they may READ but not administer they get no control at all and are told
> whose place it is.

Three states, all implemented, none of them reachable.

## Actual

The rail, read off the screen for each role:

```
Admin (company): Hierarchy Access Shifts Operators Trainings Matrix Products
                 Cycle times Import Settings Activity
Dana (site admin, Plant A):
                 Hierarchy Access Shifts Operators Trainings Matrix Products
                 Cycle times Import
```

No Settings. And the server, asked over Dana's own session about her own plant:

```
set_node_setting(plant_a, 'eligibility_policy', '__probe__')
  -> 400 {"code":"PT400",
          "details":"{\"error\": \"invalid_argument\", \"field\": \"eligibility_policy\", \"value\": \"__probe__\"}",
          "message":"unknown value for this setting"}
```

`invalid_argument`, **not** `not_permitted`. The permission gate ran and passed
her; only the deliberately illegal value stopped the write. A legal one would
have been stored.

The pin is red on this build:

```
FAIL  src/test/defects/DEF-0007.test.tsx > a site admin is offered Settings —
      the server takes their writes on their own plant
AssertionError: expected null not to be null
```

⚠️ **The Activity tab beside it is correct, and the contrast is the point.**
`audit_log_select` really is `app_is_admin() and org_id = app_current_org()`, and
Dana's own read confirms it:

```
GET /rest/v1/audit_log?select=id&limit=3   ->  200  []
```

Zero rows, not a refusal — the silent-empty the tab is hidden to avoid. So the
`companyAdminOnly` axis is right and must stay; it is being applied to one tab
too many.

## Lead

A suspicion, not a fact.

`AdminPage.tsx:115` carries `companyAdminOnly: true` on the settings row, under a
comment that reads:

```
// System-admin only (see `companyAdminOnly` note above). Org-wide preferences,
// the first being the date-display format (0037 / `src/lib/format/dates.ts`).
```

and the filter at `:322` explains itself the same way:

```
// without this a site admin would be offered Settings — an org-wide screen the
// server then refuses.
```

Both sentences were true when they were written and stopped being true two
migrations later. Settings is no longer an org-wide screen: 0050 added
`node_settings` and `set_node_setting` gated on `app_is_admin() OR
app_is_admin_for(node)`, and 0052 moved `date_format` under the same shape. The
company-scope half of the pane is still company-admin-only — `set_org_date_format`
and `set_org_eligibility_policy` are both `app_is_admin()` — and the panel
already renders that half disabled with the reason in words. It is the per-plant
half, the whole point of R-331 and R-333, that no plant admin can reach.

⚠️ **AND A GREEN CASE IS PINNING IT.** `auditAccess.test.tsx` ends with

```ts
it("Settings and Activity are gated by the same test, so neither can drift", ...)
  expect(railButton("Settings")).toBe(null);
```

That case asserts this defect is correct behaviour. It was right when Settings
and Activity really were the same question; 0050 made them different questions
and nothing revisited it. **It has to change with the fix**, and its name — "so
neither can drift" — is what makes it worth reading twice: the two tabs were tied
together to stop them drifting, and the tie is now what holds the stale one in
place.

The shape that suggests itself, and the developer decides: drop `companyAdminOnly`
from the settings row only, and let the panel's three states do the work they
were already written to do. What would make that safe to do is already there —
`canAdministerPlant` in the panel, and the server refusing anything it disagrees
with. Whether a plant admin SHOULD set their own plant's rules is the
maintainer's call; what is not a judgement call is that the client and the server
currently answer it differently, and the answer should be written down once.
