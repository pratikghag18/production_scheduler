## Reproduction

At tip `03700f1`, on the tester's own database (or any stack), after any run of
`e2e/weekTemplates.spec.ts` -- including runs from BEFORE DEF-0029 started failing, when the day of
the week was still Monday-Wednesday and the main test passed cleanly:

```
docker exec supabase_db_production_scheduler_tester psql -U postgres -d postgres -c "select name, created_at from week_templates where name like 'E2E %' order by created_at;"
```

## Expected

`e2e/weekTemplates.spec.ts`'s own file header: *"IT WRITES TO THE DEMO DATABASE and cleans up
after itself: every template is named with a per-run suffix and deleted in the admin Templates tab
at the end."* `deleteTemplate` (the helper `afterAll` calls for both `DANA_TPL` and `ANA_TPL`) is
the thing that is supposed to make this true.

## Actual

Before filing this, the tester's database carried eight `E2E %`-named templates, in two pairs dated
2026-09-09 (23:18 and 23:59 UTC -- both from tester sessions run WHILE the demo week's Monday-
Wednesday was still current, so the main test passed cleanly that day) and two pairs dated
2026-09-10 (01:12 and 01:14 UTC -- from this session, after DEF-0029 started failing the main
test). All eight were cleaned up by hand as part of filing this defect; the point is that cleanup
failed on BOTH the passing runs and the failing ones, so this is independent of DEF-0029.

Reproduced the mechanism directly with a throwaway spec that saves a template, opens the admin
Templates tab, and logs `row.count()` the moment the tab is clicked and again after a short wait:

```
row.count() immediately: 0
row.count() after 500ms: 1
delete button count: 1
```

`deleteTemplate` in `e2e/weekTemplates.spec.ts` (lines 58-64):

```ts
async function deleteTemplate(page: Page, name: string): Promise<void> {
  const row = page.locator("li", { hasText: name });
  if ((await row.count()) === 0) return;
  await row.getByRole("button", { name: "Delete" }).click();
  await row.getByRole("button", { name: "Yes, delete" }).click();
  await expect(page.locator("li", { hasText: name })).toHaveCount(0, { timeout: 15_000 });
}
```

`.count()` is a one-shot DOM read, not an auto-retrying assertion -- it does not wait for
`TemplatesPanel`'s `listWeekTemplates` query to leave its loading state. `afterAll` clicks
"Templates" and calls `deleteTemplate` right away; on the timing observed above, the query has not
resolved yet, `row.count()` reads 0 off the still-loading (or momentarily empty) list, and the
function returns believing there is nothing to delete -- the template it just created is left in
the database, permanently, every time this race is lost. The throwaway reproduction above lost the
race on its first and only attempt.

## Lead

A suspicion on the exact fix, not on the mechanism (confirmed above). `deleteTemplate` should wait
for the row the same way the rest of the file already knows how to -- `await
expect(row).toHaveCount(1, { timeout: ... })` before deciding whether to act, the way
`saveTemplate`'s own `toBeHidden` and `toBeVisible` calls already retry rather than snapshot. The
`if (count === 0) return` no-op guard is presumably there so `afterAll` does not fail when the
maintainer or an earlier failed run already removed the row by hand; that guard is still worth
keeping, just after actually waiting for the list to settle rather than reading it mid-load.

## Developer note

Fixed: `deleteTemplate` in `e2e/weekTemplates.spec.ts` now waits for the Templates list with a
retrying `await expect(row).toHaveCount(1, { timeout: 15_000 })` before deciding whether to delete,
instead of reading `row.count()` mid-load and skipping on a false zero. The genuine no-op path is
kept: if the row truly never appears the assertion times out, the `catch` returns, and `afterAll`
does not throw. ESLint clean; not run here (no live stack), the tester's cold run is the proof.

## Tester re-verification -- 10 Sept, at `3c82575`

Re-ran cold on a freshly reset tester stack. `select count(*) from week_templates` read 0 rows
after the full run completed -- both `DANA_TPL` and `ANA_TPL` were created and deleted cleanly,
confirmed directly against the table rather than inferred from a green suite. One of the three
`weekTemplates.spec.ts` cases did report `"afterAll" hook timeout of 30000ms exceeded`, but the
empty table proves the delete itself had already succeeded before that timeout fired -- read as
end-of-suite worker-contention tail latency on the LAST step of the hook, the same category
already named for `copyWeek.spec.ts`/`absences.spec.ts` in session 128, not a reopening of the
race this card describes. Verified.
